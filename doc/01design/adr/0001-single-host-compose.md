# ADR-0001：单机 Docker Compose，不引入 K8s

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-07-29 |
| 决策人 | hxy |
| 主文档关联 | §2.2 规模与部署约束、§3.2 核心权衡、§4.4 部署架构 |

## 背景

平台面向一个学院的几十到几百名教师，部署在学院 / 学校内网服务器上。需要决定编排方案：单机 Docker Compose，还是 Kubernetes。

由用户规模可推出量级判断：**同时在跑的 agent 任务大概率是个位数到几十**。

## 决策

采用**单机 Docker Compose**。不上 K8s、不做队列分片、不引入服务网格。

同时保持一条纪律：**每一层保持无状态或可水平扩展**（网关、worker 均为无状态，状态在 Postgres/Redis 中）。真撞到瓶颈时加副本即可，不需要重构。

## 理由

在几十并发的量级下，真正的瓶颈是：

1. LLM API 的 rate limit
2. token 成本
3. 沙箱容器占用的宿主机内存

**这三项没有一项是架构吞吐问题**，因此为吞吐做的分布式投入拿不到回报。

K8s 的收益（自动扩缩、滚动发布、跨节点调度、自愈）在本场景下要么用不上（只有一台服务器），要么有更廉价的替代（`docker compose up -d` 即可完成滚动重启）。而它的成本是确定的：一套需要持续维护的控制平面，在内网环境下还要自己解决镜像分发与证书轮转。

## 被放弃的备选

| 备选 | 放弃理由 |
|---|---|
| **Kubernetes** | 运维成本远超收益。单台服务器上跑 K8s，等于为了用调度器而引入一个需要被调度的系统 |
| **K3s / 轻量 K8s** | 降低了安装成本，但没有降低理解成本与排障成本。团队规模下不划算 |
| **裸机 systemd 部署** | 比 Compose 更轻，但沙箱本身依赖 Docker，容器化已是既定事实，再混一套 systemd 反而更乱 |

## 后果

**正面**：
- 部署与排障心智负担低，`docker compose logs` 就能看全貌
- 内网环境下不需要额外解决 K8s 的镜像仓库、CNI、证书等问题
- 开发环境与生产环境可以是同一套 compose 文件

**代价**：
- **单点故障**。Postgres 无冗余，宿主机故障即全局不可用（见主文档 §8.2、§10.2）
- 无自动扩缩容。容量靠事前规划（§8.1），超限时排队而非弹性伸缩
- 沙箱容器数受单机内存硬约束，约 25–30 个（64GB 服务器）

这些代价在当前规模下被判定为可接受 —— 平台是教学辅助系统，可接受计划内停机。

## 重新评估的触发条件

- 需要跨机器部署（单机内存撑不住沙箱并发）
- 应用副本数长期超过 10
- 学院对可用性提出明确 SLA 要求，单点不再可接受
