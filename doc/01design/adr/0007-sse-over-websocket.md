# ADR-0007：实时推送用 SSE，不用 WebSocket

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-07-29 |
| 决策人 | hxy |
| 主文档关联 | §4.2 三条独立通道、§5.2 事件流与断线重放、§8.4 部署与发布 |

## 背景

前端需要实时接收 agent 执行过程中的事件流。需要在 SSE 与 WebSocket 之间选择。

## 决策

采用 **SSE**（Server-Sent Events）承载服务端到前端的事件流。

客户端到服务端的交互（提交、中断、审批、追问）走**普通 REST POST**，与事件流分离 —— 这就是主文档 §4.2「三条独立通道」中控制通道与事件通道分开的由来。

## 理由

**通信模式是高度不对称的。** Agent 场景约 **95% 是服务端单向推流**（token 增量、工具调用、中间步骤），客户端交互（中断、审批、追问）频率极低 —— 一次几十分钟的分析可能只有一两次审批点击。为这点交互引入全双工协议不划算。

SSE 的具体优势：

1. **协议简单**，就是一个长连接的 HTTP 响应，不需要握手升级
2. **自带断线重连与 `Last-Event-ID`**，与 [ADR-0006](./0006-event-channel-streams-not-pubsub.md) 的 Stream 重放机制天然咬合 —— 这一点是决定性的
3. **走标准 HTTP**，对 Nginx 与校园网代理友好。WebSocket 的 Upgrade 请求在某些校园网设备上会被拦或超时，内网环境下这是真实风险

## 被放弃的备选

| 备选 | 放弃理由 |
|---|---|
| **WebSocket** | 全双工能力在本场景 95% 用不上；需要自建重连与消息补发机制（SSE 白送）；对代理不友好 |
| **HTTP 轮询 / 长轮询** | token 级别的增量推送用轮询延迟太高，体验明显劣化 |

## 后果

**正面**：
- 断线重连与事件补齐几乎零成本，直接对接 Redis Stream 的 `Last-Event-ID` 重放
- 运维简单，标准 HTTP 链路，排障可以直接用 `curl`
- 控制通道与事件通道分离，鉴权逻辑集中在 REST 侧，事件流只读

**代价**：
- **Nginx 必须改配置**，否则流式输出会被缓冲到响应结束才吐出（见主文档 §8.4）：`proxy_buffering off` + `proxy_read_timeout 3600s`。这是一个不改就完全不工作、改了就好的坑
- **前端不能用原生 `EventSource`**。平台是多租户带鉴权的，而原生 `EventSource` 不支持自定义请求头，无法携带 Authorization。需改用 `@microsoft/fetch-event-source`，代价是 `Last-Event-ID` 的维护从浏览器转到应用侧（详见[前端技术选型 §3.3](../02Frontend%20Technology%20Selection.md.md)）
- 每个 SSE 连接占用一个 HTTP 连接与网关侧一个 `XREAD` 循环，需关注连接数上限
- 若将来出现高频双向交互需求，需要重新评估

## 重新评估的触发条件

- 出现高频双向通信需求（如多人协同编辑同一分析、实时光标同步）
- SSE 连接数成为网关瓶颈且无法通过加副本解决
