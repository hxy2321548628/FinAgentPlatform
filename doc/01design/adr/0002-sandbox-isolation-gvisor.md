# ADR-0002：沙箱隔离用 Docker + gVisor，不用 Firecracker

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-07-29 |
| 决策人 | hxy |
| 主文档关联 | §7.1 威胁模型、§7.3 沙箱隔离 |

## 背景

Agent 要写并运行分析代码，代码由 LLM 生成、无法事前审查，必须视为不可信。内网部署又意味着数据不能交给外部托管的 code execution 服务（E2B、Modal 等），因此**必须自建沙箱**。

需要决定隔离强度。这是整个架构中最重的一块。

## 决策

采用 **Docker + gVisor (runsc)** 作为沙箱运行时。

落地节奏上分两步（见主文档 §11）：P0 先用**裸 Docker** 跑通全流程，P1 再切换到 `runsc` 并补齐完整加固参数。

## 理由

关键在于先定清楚**威胁模型**：

> 用户是学院教师而非匿名公网用户，威胁模型主要是**「agent 生成的代码写错了或失控」**（死循环、fork 炸弹、写满磁盘、误删文件），而不是定向的沙箱逃逸攻击。

在这个威胁模型下，gVisor 的隔离强度绰绰有余 —— 它在容器与宿主机内核之间插入一层用户态内核，拦截系统调用，把内核攻击面从数百个 syscall 缩减到极小的一组。

另一个决定性因素是**迁移成本几乎为零**：gVisor 基本是 Docker 的 drop-in 替换，切换只是加一个 `--runtime=runsc`。这使得「P0 用裸 Docker 快速验证效果、P1 再加固」的分期策略成本极低 —— 如果切换需要重写沙箱层，就不敢这么排期了。

## 被放弃的备选

| 备选 | 隔离强度 | 运维成本 | 放弃理由 |
|---|---|---|---|
| **裸 Docker** | 弱（共享宿主机内核） | 低 | 内核漏洞即逃逸。仅作 P0 起步用，**不可带入上线** |
| **Firecracker microVM** | 最强（独立内核） | 高，需要 KVM 支持 + 自建镜像流水线 | 对本规模属于过度设计。隔离强度的提升换不回运维复杂度的增加 |
| **外部托管服务**（E2B / Modal） | 强 | 极低 | 内网部署，教师的研究数据不能交给外部服务。合规上直接排除 |

## 后果

**正面**：
- 隔离强度与威胁模型匹配，不多不少
- 切换成本极低，支持「先验证后加固」的分期
- 仍在 Docker 生态内，沙箱管理代码不需要为 VM 另写一套

**代价**：
- gVisor 有**性能开销**，系统调用密集的负载（大量文件 IO）会明显变慢。pandas 读大 CSV 时可能感知得到
- gVisor 的 syscall 覆盖不是 100%，**少数依赖冷门 syscall 的库可能跑不起来**。P1 切换时需要用真实的分析场景回归验证，不能只跑 hello world
- 需要在宿主机安装并维护 runsc 运行时

## 重新评估的触发条件

- 平台对校外开放，或用户不再是实名可信的内部教师 → 需要重新评估是否上 Firecracker
- P1 切换时发现常用分析库在 runsc 下不可用且无法绕过
- 出现 gVisor 自身的高危逃逸漏洞
