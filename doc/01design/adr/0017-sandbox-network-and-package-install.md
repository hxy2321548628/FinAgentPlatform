# ADR-0017：沙箱开放出网，agent 自己装 Python 包

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-08-18 |
| 决策人 | hxy |
| 关联设计 | [安全设计 §7.3.3、§7.3.4](../07security-design.md) |
| 推翻 | [P1 计划 §2.2](../../03plan/P1-plan.md) 的「保持 `--network=none`」 |

## 背景

P1 定案沙箱 `--network=none`，agent 装不了任何包，缺库只能把库加进沙箱镜像重新构建。当时列的重估触发条件是「分析需求反复撞到缺库，且加库频率高到无法靠重建镜像跟上」——本次由使用方直接提出放开，触发条件成立。

P1 真正卡住的**不是网络**，而是加固清单里没有一条**既可写又可执行**的路径：`--read-only` 让 `pip` 只能装到 `HOME`，而 `HOME=/tmp` 是 512 MB 且 `noexec` 的 tmpfs——装得下的包跑不起来，跑得起来的包装不下。所以「开个网」并不能让 `pip install` 变得可用，两件事必须一起解。

## 决策

三条一起，缺一条这个功能就是坏的：

| 项 | 取值 |
|---|---|
| 网络 | `--network=bridge`，直连外网，**不做 iptables 白名单** |
| 安装位置 | `PYTHONUSERBASE=/workspace/.local`，配 `PIP_USER=1` |
| 索引源 | `PIP_INDEX_URL` 与 `UV_INDEX_URL` 双设，默认清华源（`SANDBOX_INDEX_URL` 可配） |

**加固清单一条未动。** `--read-only`、`--cap-drop=ALL`、`--security-opt=no-new-privileges`、非 root、gVisor、5 GB XFS 配额全部原样保留。

**只放开 Python 包，不放开系统包。** 容器内没有 root，`apt-get` 必然失败（实测报 `are you root?`），这是刻意保留的边界。

## 理由

**装到 workspace，是「可写且可执行」的唯一现成答案。** 它是 bind mount：可写、没有 `noexec`、随会话持久（同一会话装一次就够）、且本来就被 5 GB XFS 配额兜着——装爆了只影响这一个会话，不影响宿主机。因此不必为装包去动加固清单里的任何一条。

**不做白名单 bridge，尽管它收得更紧。** 沙箱容器由 broker 在运行时按会话动态创建与销毁，iptables 规则要跟着每个容器的生命周期走；这套东西一旦配错**没有任何症状**（就像 XFS 配额那次，[ADR-0015](./0015-sandbox-disk-quota-xfs.md)），却要长期维护。而在[威胁模型](../07security-design.md)下——用户是实名可信的校内师生，主要威胁是「代码写错了」而非定向攻击——白名单挡住的攻击本就不在模型内。

**不装 apt，不是因为难，而是因为不划算。** 要 root 就得去掉 `--read-only`、放开 `cap-drop`、去掉 `no-new-privileges`，等于把 gVisor 之外的纵深防御全拆了；而容器是 per-thread 可抛弃的，apt 装的东西随容器销毁就没了，每个会话都要重装一遍——付出全部安全代价，换不到持久性。

**镜像源是可用性前提，不是优化。** 实测直连 pypi.org 只有 83 KB/s，一个 scipy 要 9 分 51 秒，会直接撞上单次执行的 wall-clock 超时；换清华源后同样的包 14 秒。

## 被放弃的备选

| 备选 | 放弃理由 |
|---|---|
| **维持 `--network=none`** | 就是被本次需求推翻的现状 |
| **白名单 bridge**（只放行镜像源） | 规则要跟着动态容器走，配错无症状；挡的攻击不在威胁模型内 |
| **共享的 site-packages 卷**（跨会话复用，只装一次） | 一个会话装的包会被别的会话加载——在跑不可信代码的地方开了条会话间投毒通路 |
| **去掉 `--read-only`，装进 rootfs** | 拆掉刻意标注「不做成配置项」的加固项，且容器销毁即丢，不持久 |
| **自建 devpi / 内网 pypi 镜像** | 多一个要运维的服务，而公网镜像源已经够快 |

## 后果

**正面**：
- agent 不再因缺库直接卡死，且不必为每个冷门库重建镜像
- 加固清单零改动，安全边界的其余部分不受影响
- 装的包落在 workspace，天然被既有配额机制约束

**代价**：
- **沙箱里的代码可以把 workspace 的内容发到任意地址**。gVisor 之外没有第二层网络管控，这是本决策换来装包能力所付的主要代价
- 装的包吃教师那 5 GB 配额（scipy + statsmodels 实测 185 MB），且不同会话各装各的
- 沙箱行为多了一个外部依赖：镜像源不可达时装包失败

**实现上四个会静默失效的点**（每个都实测过，见[安全设计 §7.3.3](../07security-design.md) 的表）：`PIP_USER=1`、`PIP_CACHE_DIR` 躲开 tmpfs、`UV_INDEX_URL` 必须与 `PIP_INDEX_URL` 同时给（uv 完全忽略后者）、提示词必须同步告诉 agent 能装包。

## 重新评估的触发条件

- **平台对校外开放，或用户不再是实名可信的校内师生** —— 此时要连同 [ADR-0002](./0002-sandbox-isolation-gvisor.md) 一起重估，白名单 bridge 会重新变得划算
- 出现沙箱代码外发数据的实际事件
- 装包占用把 workspace 配额顶到频繁触顶
