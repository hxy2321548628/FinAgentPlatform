## 路线基线

这张表原为总体架构 §11。拆分后移到实施计划索引，保留各期最初承诺与验收口径；具体定案和最终结果以上方各期计划为准。

| 阶段 | 内容 | 验证标准 |
|---|---|---|
| **P0** | FastAPI 内运行 DeepAgents、裸 Docker 沙箱、SSE 流式输出 | 用户能对话；Agent 能写 Python 读 CSV、计算并返回图表 |
| **P1** | gVisor、资源与磁盘配额、Sandbox Broker、生命周期管理 | 死循环、fork 炸弹、写满 workspace/tmp 均不影响宿主机 |
| **P2** | Redis Streams、Postgres Checkpointer、Run 与事件元数据 | `kill -9` Worker 后从 checkpoint 续跑，已完成步骤不重做 |
| **P3** | HITL、取消、多用户隔离、配额限流、工具幂等 | 审批走通；崩溃恢复不重复写；30 并发不崩溃、不串数据 |
| **P4** | OpenTelemetry、MinIO 产物、成本看板 | 能定位单个 Run 的完整 Trace 与 Token 花费 |

验收脚本在 [`deploy/test/`](../../deploy/test/)：`p1.sh` 转调 `hostile.sh`（破坏性四条）与 `acceptance.sh`（P0 回归四条），`p2.sh` / `p3.sh` / `p4.sh` 逐级往下转调，**跑 `p4.sh` 等于把五期一起跑一遍**。每条判据该看到什么、失败时看哪里，写在各期计划的 §4 与 §8。

> **两套验收脚本不能同时跑** —— 它们共用同一套 compose 栈，而 `p2.sh` 那一层会 `kill -9` 进程来造崩溃场景。同时跑的结果是双方都红，且红在互不相干的地方（[P4 §8.10.1](./P4-plan.md) 实测踩过）。

> **每份计划的固定骨架**：§1 边界（做什么／不做什么，不做的每条写明由哪期偿还）→ §2 与上游文档不一致处的本期定案 → §3 环境前提 → §4 验收标准（一条命令能跑完）→ §5 任务分解（每步独立可验，未过不进下一步）→ §6 回归关系 → §7 待决事项。
>
> **§1.3 的「明确不做」是这套文档最该认真读的一节** —— 它是技术债的登记簿。每条都带偿还期次，翻一遍就知道现在的平台差在哪，而不必去猜。
