## 2. 开工前实测与本期定案

**六处已跑完，两处推翻了决策文档的预设。**

### 2.1 Langfuse 的端点边界 —— 测了两轮，第一轮是错的

[P13-decision C6](./P13-decision.md) 记着完整对照表。**这里只记与本计划有关的三条**：

- 数据集、prompt、score-config、annotation-queue **可用** —— 评估集有地方放、rubric 有地方托管、人工抽检有正式载体；
- 分数与实验结果 **读得回来**（`/api/public/v3/scores`、`/experiments`、`/experiment-items?fields=io`），因此本地 JSON 是便利副本而非唯一通路；
- trace 与 session 的读取在 v4 **真的取消了**，没有替代 —— 内容挂在 observation 上（`/v2/observations`）。

> ⚠️ **第一轮结论「写得进读不回」是错的**，错在只测了 v3 遗留端点、且把 404 响应体截断了（`_deprecation.replacement` 字段正好被切掉）。**教训写进本计划的 §3 环境前提**：打到 4xx 先完整打印响应体。

### 2.2 DeepSeek 吃不到任何 prompt-caching 中间件 —— **推翻 A2 的预设**

deepagents 的 `append_prompt_caching_middleware()` 只装三家：`AnthropicPromptCachingMiddleware`、Bedrock、Fireworks，且都带 `unsupported_model_behavior="ignore"`。**DeepSeek 一个都不沾，装了也是空转。**

这不是坏消息，因为 DeepSeek 的 prompt cache 是**服务端按前缀自动命中**的（平台实测 62% 与 31% 就是证据，见 [P13-decision §2](./P13-decision.md) 第 4 条）。

> **A2 的形状因此变了**：不是「装一个缓存中间件」，而是 **「审计前缀里有没有每轮都变的内容，并把这条规则钉进代码」**。能做的事只有一件 —— 让前缀稳定。步骤五因此与 A8 合并：新增的动态内容一律走尾部注入点。

### 2.3 压缩阈值可以钉死，路径是「按中间件名替换」

`create_summarization_middleware()` 这个公开构造器**不暴露阈值**（只有 `summary_prompt` / `trim_tokens_to_summarize` / `token_counter`），阈值来自 `compute_summarization_defaults(model)` 从模型 profile 推出来的 `('fraction', 0.85)` × `max_input_tokens=1000000`。

但实现类 `_DeepAgentsSummarizationMiddleware.__init__` **接受 `trigger` 参数**，且它的 `.name` 报的是公开别名 `"SummarizationMiddleware"`；而 `_apply_custom_middleware()` 的规则是 **「custom 里 `.name` 与基础栈里某个重名就原地替换，保持栈序」**。

> **因此 A1 的落地路径是**：平台自己构造一份 summarization 中间件、显式传 `trigger=("tokens", 平台常量)`，作为 custom middleware 传进 `create_deep_agent` —— 它会替换掉基础栈里那个，而不是叠加一份（叠加正是 [A1](./P13-decision.md) 否掉的选项 a）。**替换是否真的生效，是步骤三的验收判据，不是假设。**

### 2.4 撞递归上限现在混在 `INTERNAL` 里 —— 位置已定位

[`executor.py:274`](../../src/app/run/executor.py#L274) 是一句 `except Exception as exc:` 直接落 `RunErrorCode.INTERNAL`。`GraphRecursionError` 走的就是这一支，全仓 `grep recursion` 没有任何一处认它。

**改动面很小**（加一个 `except GraphRecursionError` 分支 + 一个枚举值 + 前端文案），但它是**尺子的一部分**：`error_code` 是 13 项指标之一，撞上限分不出来，失败归因那一栏就是坏的。

### 2.5 `compaction_count` 没有采集通路 —— 本期要补

deepagents 把压缩事件放在私有 state 字段 `_summarization_event`，并把每次压缩追加进一个文件。**平台的事件流里没有任何一种事件对应它**（`EventType` 枚举里没有）。

A1 的主指标就是这个数。**不补通路，A1 改完无法验证是否生效。**

### 2.6 评估集与数据已先行落地

写本计划时为验证「判据写得出来吗」，先造了首批 10 题并上传：

| 落地物 | 位置 |
|---|---|
| 10 题与判据 | [`script/eval/dataset.json`](../../script/eval/dataset.json) |
| 幂等上传脚本 | [`script/eval/upload_dataset.py`](../../script/eval/upload_dataset.py) |
| 数据（含注入的异常值、固定种子的日频生成器） | [`script/eval/data/`](../../script/eval/data/) |
| Langfuse 数据集 | `zuel-finance-eval-v1`（10 条 item，已读回验证） |

**probe 覆盖 9 种**：基线 ×2、缺失值、异常值、装包、审批闸门、中文图表、压缩、多轮记忆、不存在的字段。ground truth 是算出来的不是估的（例：行业占比 31.98%／19.57%，年化波动率茅台 0.2010、招行 0.0804，锚题 0.10385374331241026）。

| 前提 | 怎么确认 |

## 4. 验收标准

**分两组，因为它们的成本差两个数量级。**

### 4.1 进 `verify.sh` 的（免费或极便宜，判据总数 62 → 66）

| 判据 | 该看到什么 | 失败时看哪里 |
|---|---|---|
| **P13①** | 撞递归上限的 run 记成 `RECURSION_LIMIT` 而不是 `INTERNAL`：把上限配成极小值跑一道普通题，`runs.error_code` 与 `run.failed` 事件里都是新码，前端文案可读 | `executor.py` 的异常分支；上限是不是真的读到了配置 |
| **P13②** | 压缩触发得到、也数得出来：把阈值配成极低值跑一道普通题，事件流里出现压缩事件且计数 ≥ 1；恢复正常阈值后同一道题计数为 0 | 采集通路接在哪一层；`_summarization_event` 是否被 checkpoint 短路（P8 踩过同型） |
| **P13③** | 阈值是平台的显式常量且**替换真的生效**：图里那个 summarization 中间件是平台构造的那份，不是 profile 推出来的那份 | `_apply_custom_middleware` 的按名替换是否命中（§2.3） |
| **P13④** | 尾部注入块落在**最后一条 user message 之后**，块不进 checkpoint，且总量不超过预算上限 | `wrap_model_call` 的 `override(messages=...)`；块的 token 计数 |

> **P13① 与 P13② 都要「配成极端值再跑一次」** —— 这是[§9 总原则](./P13-decision.md)的直接落地：判据要能回答「这次真的触发了要测的场景吗」，而不是「这次没报错吗」。**两条都必须能在正常配置下复原为不触发**，否则证明的只是「它一直在报」。

### 4.2 评估集那一组（要真实 LLM 费用，按需跑，不进门禁）

| 判据 | 该看到什么 |
|---|---|
| **P13⑤** | **本期的主判据**：同一批 10 题，改造前后的 `cache_hit_rate` 与 `compaction_count` 并排可比，**差值超出 P13⑥ 那条噪声带**才算改进 |
| **P13⑥** | **确定性指标的噪声带**（本期必须）：10 题 × 3 副本，同题的 `cache_hit_rate`、`tokens_uncached`、`llm_rounds` 极差有数。**没有这条，P13⑤ 就只是两个数字大小的比较** |
| **P13⑦** | **尺子自身的校验**：`probe_coverage` 报得出「这批里几题真的触发了压缩、几题真的撞了审批、几题真的装了包」。**任一 probe 命中数为 0 时，那一栏记「未验」不记「过」** |
| **P13⑧** | **判分噪声带**（步骤八，首轮不接 judge 的欠账）：同题三副本的 `plan_quality` 极差有数。**这个值决定 P15 的验收标准长什么样**（[D5](./P13-decision.md)） |

## 6. 回归关系

| 本期改动 | 可能打穿 |
|---|---|
| `executor` 新增错误码分支 | P2（崩溃恢复）、P3（取消与 HITL）的失败路径判据；前端的失败文案（P6 走查） |
| 中间件栈里多一份平台自己的 summarization | **P0①–⑤ 全部**（每一次分析都过这条栈）、P8（skill 中间件同栈）、P9（子图各自装一份） |
| 尾部注入块改变每轮的消息构成 | P4 的 token 判据、P11 的用量归属与账单对账 —— **块本身要烧 token，两边的数都会变** |
| 事件模型新增压缩事件 | 前端的事件 schema 校验（web 那份照着 `event/model.py` 抄的）、P6 的 SSE hook |
| `RECURSION_LIMIT` 由常量改配置 | P9 的递归上限判据（子图那个 9999 是框架硬编码的，不受影响，但判据文案要对得上） |

> **步骤六是本期最容易打穿别人的一步** —— 它改变每一次模型调用的消息构成。**步骤七的对比跑之前，先跑一遍免费那 43 条**，否则「分数变了」分不清是改进还是打穿。

## 7. 待决事项

**开工前那三处已经问掉并定案**（§2.7）。剩下的两条**只能等数据**，不是没问：

1. **尾部注入块的 token 预算上限定多少。** 现在定不了 —— 它取决于步骤五探出来的真实上下文上限。上限若远小于 profile 报的 100 万，块的预算就得跟着缩，否则挤掉的是对话本身。**步骤五出数之后立刻回填这里。**
2. **首轮跑完要不要重造题。** [C1 的选择性偏差](./P13-decision.md)是主动接受的代价：造题的人知道 agent 会做什么。**判断标准写在前面**——首轮若接近全过、或 `probe_coverage` 明显低于 1（题目根本没走到要测的路上），就按 C1 的缓解清单重造一批。**一批全过的评估集不是好评估集，是没校准的评估集。**
