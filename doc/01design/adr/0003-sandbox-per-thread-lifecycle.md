# ADR-0003：沙箱按 thread 长驻，不做 per-call

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-07-29 |
| 决策人 | hxy |
| 主文档关联 | §5.5 沙箱生命周期、§8.1 并发模型与容量 |

## 背景

需要决定沙箱容器的生命周期粒度：每次 `execute_python` 调用开一个新容器（per-call），还是一个会话共用一个容器（per-thread）。

## 决策

**按 thread 长驻**：

- thread 首次需要执行代码时分配容器
- 同一 thread 的后续代码调用**复用**该容器
- idle 30 分钟无调用则回收
- 下次需要时重建，workspace 文件从卷恢复

配套要求：文件状态必须留在容器之外的卷里，容器本身无状态可抛弃。

```
沙箱容器 /workspace
    ↕ bind mount
宿主机 /data/sandbox/{thread_id}/
    ↕ 异步同步
MinIO tenant/{user_id}/thread/{thread_id}/
```

## 理由

Agent 完成一次分析是**分多步执行代码**的：先 `pip install`，再读数据，再计算，再画图。

如果每次调用都开新容器，前一步装的包和写的文件全部丢失 —— agent 会陷入「装包 → 下一步发现包没了 → 再装」的死循环，既跑不出结果，也浪费大量 token 和时间。

per-thread 复用让**包、文件、中间结果**在整个会话内保持连续，这与 DeepAgents 虚拟文件系统的语义也天然对齐（虚拟文件系统直接映射到该 workspace）。

## 被放弃的备选

| 备选 | 放弃理由 |
|---|---|
| **per-call**（每次调用新容器） | 状态全丢，agent 无法完成多步分析。**功能上不可行**，不只是效率问题 |
| **per-user 长驻**（一个教师一个容器） | 粒度过粗。同一教师的不同研究课题会互相污染工作目录与已装的包版本 |
| **永久长驻**（不回收） | 内存是硬约束（§8.1），不回收会迅速耗尽宿主机内存 |

## 后果

**正面**：
- agent 能完成真正的多步分析，这是平台的核心价值
- 容器可随时销毁重建（状态在卷里），故障恢复简单
- 避免重复 `pip install` 带来的时间与流量浪费

**代价**：
- **内存成为容量瓶颈**。活跃 thread 数 ≈ 可用内存 / 单沙箱上限(2GB)，这是 §8.1 全部容量规划的来源
- 需要实现 **SandboxManager**：容器数上限、LRU 回收、超限排队、健康检查、idle 计时。这是一块实打实的工程量
- 长驻容器可能积累脏状态（装了冲突的包版本），agent 可能被自己早先的操作绊住。需要提供「重置沙箱」能力

## 重新评估的触发条件

- idle 30 分钟这个阈值需要按真实使用数据调整（教师可能长时间思考后再追问）
- 若内存瓶颈显著早于预期到来，可考虑「快照 + 冻结」替代常驻（把 idle 容器的文件系统快照后销毁，恢复时从快照重建）
