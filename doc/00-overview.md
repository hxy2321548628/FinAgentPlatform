## 1. 这个平台是做什么的

中南财经政法大学金融学院的教师，面对日常的科研与教学数据，常常需要跑 Python 分析：读数据、算指标、画图表。但大多数教师不会写代码。

这个平台做的事，一句话就能说清：**教师用自然语言提问，智能体自己写 Python，在一个隔离的沙箱里执行，然后把结论、图表和文件交回给教师。**

举一个真实的用法：教师问「把我上传的这份收益率数据做描述性统计，再画一张时序图」。智能体自己写代码、自己执行、出错自己改，最后教师拿到一张图和一份报告。

几个关键的背景数字，请先记住：

- 部署形态是**内网单机**：一台 32 核 / 64 GB 的服务器，Docker Compose 编排；
- 用户规模是**一两百人**：教师及其课题组研究生；
- 开发方式是**单人 + AI 辅助**，P0–P12 共十三期已开发完成并通过验收（见 `doc/03plan/` 各期记录），当前状态是「链路跑得住」，正在走向真实投用。

> **本节要点**：这是一个让不会写代码的人用自然语言做数据分析的平台，内网单机部署，服务于一两百名师生。

## 2. 两个贯穿全局的事实

理解这个项目，其实只需要先接受两个事实。**后面几乎所有「奇怪」的设计，都能归结到这两条上。**

**第一个事实：任务是长的。** 一次分析可能持续几分钟到几十分钟——智能体要写代码、装包、执行、画图，中途还可能被人工审批打断。这意味着一件事：一次 HTTP 请求不可能同步承载整个过程。所以平台必须是异步的：提交之后立刻返回，执行在后台进行，进度通过事件流推给浏览器。

**第二个事实：代码是不可信的。** 沙箱里跑的 Python 是 LLM 生成的，没有人预先审查过。它可能死循环、可能写满磁盘、可能有恶意行为。所以平台必须把它隔离开：它不能碰数据库，不能碰其他用户的数据，不能碰宿主机的文件系统边界。

把这两个事实合起来，就得到了这个系统最核心的两条设计主线：

1. **一条异步流水线**——提交、排队、执行、回流的全过程，状态可以持久、可以恢复、可以重放；
2. **一道隔离边界**——可信的应用层（api、worker）与不可信的执行层（沙箱）之间，只留一个窄窄的受控通道。

带着这两条主线去读代码，每一处设计都会显得顺理成章。

> **本节要点**：任务长，所以必须异步；代码不可信，所以必须隔离。这两条解释了整个架构。

## 3. 全景：六个服务 + 动态沙箱

先看一张总图。生产环境由 Docker Compose 拉起**六个服务**：nginx、api、worker、broker、Postgres、Redis。注意，**沙箱容器不在这六个里面**——它由 broker 在运行时按会话动态创建和销毁。

worker 只有一个进程。**吞吐不来自副本数**——一次分析绝大部分时间在等模型和等沙箱，一个进程内并发驱动几十个 run 就够了（`WORKER_CONCURRENCY`）；进程本身出事怎么办，见第 8 节的机制一与机制六。

```
教师浏览器 ──REST/SSE──▶ nginx ──/api/*──▶ api ──XADD 任务──▶ Redis Stream ──XREADGROUP──▶ worker
                                                                            │
                               broker ◀──── HTTP（仅内部网络）────────────────┘
                                 │ docker.sock
                                 ▼
                     沙箱容器（gVisor · 可出网 · XFS 配额 · 每 Thread 一个）
```

进度回流走另一条线，两边都要过 Redis，但各干各的：

```
worker ──XADD 事件──▶ stream:run:{id} ──XREAD 回放──▶ api ──SSE──▶ 教师浏览器
```

六个服务的分工如下：

| 服务 | 职责 | 一句话 |
|---|---|---|
| nginx | 静态托管前端、反向代理 `/api/`、SSE 透传 | 浏览器只认识它 |
| api | 登录鉴权、配额、REST、SSE 回放 | 网关，不碰 Docker、不碰 workspace |
| worker | 消费任务、驱动智能体、调 LLM、写事件 | 不是 HTTP 服务，不开端口 |
| broker | 管理沙箱容器与 workspace 文件 | **唯一持有 docker.sock 的进程** |
| Postgres | 用户、会话、run、事件归档、checkpoint | 核心持久状态 |
| Redis | 任务队列、热事件、登录态、限流计数 | 可过期的运行期状态 |

有一个很漂亮的工程决策值得单独说：**api、worker、broker 三个进程用的是同一份代码、同一个 Docker 镜像**，差别只在 compose 里给的启动命令。api 的入口是 `app.api.app`，worker 是 `python -m app.worker.main`，broker 是 `app.broker.app`。三个进程共享所有的模型和工具代码，却各司其职——这大大降低了维护成本。

> **本节要点**：六个常驻服务加运行时动态创建的沙箱；后端三个进程同一份代码同一镜像，只有入口不同。

## 4. 一条消息的旅程（主线）

理解了这张图，我们跟踪一次真实的用户提问，把整条链路走一遍。这一步是本项目阅读的**主线**，后文所有模块都在为这条链路服务。

| # | 环节 | 进程 | 代码位置 | 发生了什么 |
|---|---|---|---|---|
| 1 | 提交 | api | `app/api/route/run.py` | 教师点发送，`POST /api/runs` 进入网关 |
| 2 | 解析冻结 | api | `app/run/submitter.py` | 把 agent、skill 等**目录引用解析成快照**并冻结；解析不出来直接硬失败 |
| 3 | 投递 | api | `app/task/queue.py` | 把任务 `XADD` 进 Redis Stream，run 落库为 `queued` |
| 4 | 领取 | worker | `app/worker/main.py`、`app/worker/loop.py` | worker 用 consumer group 认领任务，run 转 `running` |
| 5 | 执行 | worker | `app/run/executor.py` | 领沙箱、驱动智能体图、翻译事件、写终态 |
| 6 | 装配 | worker | `app/agent/factory.py` | 把一次 run 的配置拼成可执行的 LangGraph 图——**与框架的唯一接触面** |
| 7 | 沙箱 | worker→broker | `app/sandbox/`、`app/broker/runtime.py` | 文件读写由 broker 直接操作宿主机 workspace；只有 `execute` 进容器 |
| 8 | 翻译 | worker | `app/event/mapper.py` | DeepAgents 的流被翻译成**平台自己的事件词汇**；不认识的 chunk 记警告后跳过 |
| 9 | 双写 | worker | `app/run/log.py` | 每个事件同时写 Redis Stream（热）和 Postgres（历史归档） |
| 10 | 回流 | api | `app/api/sse.py` | 前端订阅 SSE 增量接收；断线靠 `Last-Event-ID` 补齐 |
| 11 | 审批 | api/worker | `app/run/approval.py`、`decision.py`、`replay.py` | 命中敏感操作时 run 挂起；教师决策后作为**新任务**重投，从 checkpoint 续跑 |

有几个环节值得停下来细看：

**环节 2 的「冻结」**：提交那一刻，平台把 agent 引用解析成具体版本、把 skill 引用解析成具体名称，写进快照。此后执行侧只读快照，不再重新解析。这样即使执行过程中有人修改了配置，正在跑的 run 也不受影响。反过来，解析不出来就硬失败——绝不静默回退到默认提示词，因为那样「跑得完、不报错，唯一症状是回答变味」，是最难排查的故障。

**环节 8 的「翻译」**：worker 消费的是 DeepAgents/LangGraph 的流，但前端不能依赖框架的内部结构——否则框架一升级前端就得跟着改。所以中间竖起一道防腐层，把框架事件映射成平台事件，比如 `token`（正文）、`reasoning`（思考过程）、`tool_call`、`tool_result`。**思考过程和正式答复是两个字段、交替流出**，必须分开映射，否则前端会把它们混在一起渲染。

**环节 11 的「审批」**：当智能体要执行敏感操作时，run 进入 `waiting_approval` 状态挂起。这个状态设计得很克制——**既不占队列消息，也不占沙箱**，教师想多久再决策都行（24 小时超时转取消）。教师决策后，不是「原地继续」，而是作为一条新任务重新入队，worker 从 checkpoint 接着往下走。

> **本节要点**：一条消息的旅程 = 提交冻结 → Redis 队列 → worker 执行 → broker 管沙箱 → 事件翻译双写 → SSE 回流 → 审批挂起后从 checkpoint 续跑。

## 5. 三条通道

上一节的链路里，实际上横跨了三条职责完全不同的通道。把它们分开看，是理解事件模型的关键：

| 通道 | 载体 | 用途 | 语义 |
|---|---|---|---|
| 控制通道 | HTTP REST | 登录、提交、取消、审批、查询 | 请求-响应，同步 |
| 任务通道 | Redis Stream + consumer group | api 向 worker 投递任务 | **至少一次**投递 |
| 事件通道 | 每个 run 一条 Redis Stream + SSE | worker 写进度，api 回放给浏览器 | 可持久、可重放 |

三条通道有两个设计点值得讲：

**为什么事件通道不用 Pub/Sub？** 因为 Pub/Sub 不持久——教师刷新页面或网络抖一下，中间过程就永久丢了。对一个跑几十分钟的任务，这不可接受。所以每个 run 用一条 Redis Stream 当事件日志，断线重连时前端把最后处理过的事件 id 放进 `Last-Event-ID`，后端从中补齐；整页刷新则是从 Stream 起点重放，重建完整对话。

**为什么事件 id 直接复用 Redis Stream ID？** 形如 `{毫秒}-{同毫秒内序号}`，天然单调递增，天然适合做断点续传的游标，不需要另造一套序号。

还有一个刻意设计的解耦：**提交与订阅是两回事**。提交接口立刻返回 202 和 run_id，前端再单独发起 SSE 订阅。这样刷新页面、换设备，都不会丢失执行进度。

> **本节要点**：控制走 REST，任务走 Stream 队列，进度走「每 run 一条 Stream + SSE」；提交与订阅解耦，事件可随时重放。

## 6. 数据住在哪里

持久化层只剩两个存储，加上一类文件。它们的职责不互相替代：

| 存储 | 装什么 | 特点 |
|---|---|---|
| **Postgres** | 用户、会话（thread）、run、事件归档、agent 目录、checkpoint | 可查询的权威业务事实 |
| **Redis** | 任务队列、热事件、登录态、限流计数、MCP 熔断计数 | 低延迟、可过期；重启 = 全员重新登录 |
| **宿主机文件** | 每个 thread 的 workspace 目录（`/data/sandbox/{thread_id}/`） | 二进制产物不落库，nginx 直发 |

四件事值得记住：

1. **事件同步双写**：Redis Stream 存热的（有 MAXLEN 和 TTL），`run_events` 表存历史。异步归档会在「裁剪」与「归档」之间留一个不报错的空白窗口——这是已知取舍。
2. **checkpoint 表不进迁移**：那几张表由 LangGraph 自己 `setup()` 创建，Alembic 一个脚本都不管它们，改表结构时不要碰。
3. **thread 与 workspace 的关系**：`threads` 表是「会话存不存在」的权威，workspace 目录只是它的副产品。越权过滤长在表上，不长在文件系统上。
4. **配额也在这里**：每个 thread 的 workspace 有 5 GB 的 XFS project quota，配额设置失败时 fail-closed——宁可跑不起来，也不放一个没有配额限制的沙箱出来。

> **本节要点**：Postgres 存事实与历史，Redis 存热数据与会话，文件只活在 workspace 目录；事件双写，checkpoint 表由框架自管。

## 7. 安全与信任边界

这个项目在安全上的核心思路，不是「层层设防」，而是**把不可信执行面的接触点压到最小**。整个系统只有三条边界不可越：

1. **api 和 worker 都不挂 `docker.sock`、都不挂 workspace 目录**。一切沙箱与文件操作走 broker 的 HTTP。谁想碰 Docker，只能通过 broker 的受限接口（ADR-0004）。
2. **沙箱必须 `--runtime=runsc`**，rootfs 只读、非 root、2 GB 内存、1 CPU、128 进程数、5 GB XFS 配额（ADR-0002、ADR-0015）。生成的代码跑在一个资源受限的 gVisor 容器里。
3. **数据库迁移只由 api 容器跑**。worker 由看门狗管着、出事会自动重启，让它也 upgrade 等于把 DDL 放进一条可能反复重来的路上。

沙箱的隔离参数值得展开一句：gVisor 在容器和内核之间加了一层用户态的系统调用拦截，rootfs 只读、去掉 capabilities、非 root 运行。模型请求只由 worker 发起，不经过沙箱。

**沙箱的网络是 P12（2026-08-18）唯一放开的一条**：从 `--network=none` 改成 `bridge`，让 agent 缺库时能自己 `pip install`（装进 workspace，吃它那 5 GB 配额）。加固清单的其余各条一字未动。代价要说清楚——**沙箱里的代码从此可以把数据发到任意地址，gVisor 之外没有第二层网络管控**，这条成立的前提是威胁模型里的用户是实名可信的校内师生（ADR-0017）。仍然装不了系统软件：没有 root，`apt-get` 必然失败。

认证授权走的是简单清晰的路线：自建账号 + Cookie Session（存在 Redis）+ 角色（admin / teacher / student，2026-08-13 补了 reviewer）。`api/security.py` 只回答「你是谁」，而「你能不能看这一条」落在各 repository 的查询过滤条件上——越权资源与不存在的资源统一表现为 404，不向前端泄露资源是否存在。

一个被明确接受的取舍：内网部署用 HTTP，Session Cookie 不能设 `Secure`，这个风险在现有威胁模型下被明确记录并接受（ADR-0012）。

> **本节要点**：三条不可越的边界——api/worker 不碰 Docker 与 workspace、沙箱跑在 gVisor 里且资源受限、迁移只由 api 跑；越权与不存在统一 404。沙箱自 P12 起可出网装包，代价见上。

## 8. 可靠性：挂了怎么办

可靠性设计可以浓缩成六个机制，每个都对应一个真实故障场景：

**机制一：至少一次投递，ack 写在 `finally` 里。** worker 正常结束和业务失败都会确认消息；只有「没机会走到 finally」的死法（被强杀、被看门狗结束）才会留下未确认消息，由重启后的 worker 用 `XAUTOCLAIM` 认领回来——那条命令只看消息闲置了多久，不看它归谁，所以单副本下认领的就是重启后的自己。重复执行因此是定义而不是 bug。

**机制二：checkpoint 续跑。** 每个 run 的状态由 LangGraph Checkpointer 持久化在 Postgres。worker 崩溃后任务重投，图从 checkpoint 继续，而不是从头再来。

**机制三：幂等键。** 崩溃若发生在工具执行途中，该节点会整个重跑。所以写操作由 broker 按稳定键去重，避免重复副作用（ADR-0014）。

**机制四：重试分两层。** 调用级（单次 LLM 调用、单次 broker 请求）在 worker 内部指数退避重试，这是消化瞬时故障的主要手段；run 级**不自动重试**——失败时只在 `run.failed` 事件里给出 `retryable` 标志，重不重试由教师决定。把判断交给人，比让系统盲目重跑安全。

**机制五：人工审批不占资源。** 挂起的 run 不占队列消息、不占沙箱、不占并发配额，教师可以放心地拖到第二天再看。

**机制六：看门狗盯着事件循环。** 进程崩掉退出，Docker 的 `restart` 会把它拉回来；难办的是**进程还活着但事件循环不转了**——任务照领，然后永远不动，而单副本没有兄弟进程能发现这件事。所以 worker 里有一个守护线程盯着事件循环定期盖的时间戳，60 秒没更新就结束进程，把「卡死」变成「退出」交给 Docker。**为什么不用 healthcheck**：compose 的 `restart` 只认进程退出，判出 unhealthy 并不会重启容器，那是 Swarm 才有的行为。判据是「事件循环还调度得动」而不是「有没有进展」——后者会把每一次正常的几十分钟长分析都误杀。

另外还有两个守护性质的定时任务值得一提：`app/run/reaper.py`（孤儿收割——库里还活着、队列里已经没有它的 run）、`app/run/approval.py`（审批超时清扫），加上 `app/store/retention.py`（保留期清理），都是跑一次即退出的形态。

> **本节要点**：至少一次投递 + finally ack + checkpoint 续跑 + 幂等键 + 调用级重试 + 看门狗；run 级不自动重试，把决定权交给人。

## 9. 关键决策一览（ADR 速览）

架构决策记录在 `doc/01design/adr/`，共 18 条。不需要全读，但标注 ★ 的五条建议先读——它们对应代码里最难懂的五处设计：

| ADR | 决策 | 一句话结论 |
|---|---|---|
| 0001 | 部署拓扑 | 单机 Docker Compose，不提前分布式化 |
| 0002 ★ | 沙箱隔离 | Docker + gVisor |
| 0003 | 沙箱生命周期 | 每 Thread 一个、按需回收，不是每次调用开新容器 |
| 0004 ★ | Docker 权限 | 只有独立 broker 持有 docker.sock |
| 0005 | 任务队列 | Redis Streams |
| 0006 | 事件通道 | 用 Stream 不用 Pub/Sub |
| 0007 | 浏览器推送 | SSE，不用 WebSocket |
| 0008 ★ | 恢复机制 | LangGraph Checkpointer |
| 0009 | 模型选择 | 主模型 deepseek-v4-pro + 辅助任务下沉轻量模型 |
| 0010 | 认证授权 | 自建账号 + RBAC |
| 0011 | 会话 | Cookie Session，不用 OAuth2 |
| 0012 | 传输安全 | 内网明文 HTTP，接受无 Secure Cookie |
| 0013 ★ | 事件边界 | 平台事件防腐层，不透传框架事件 |
| 0014 ★ | 写操作恢复 | Broker 侧幂等去重 |
| 0015 | workspace 配额 | XFS project quota |
| 0016 | Agent 文件系统 | 自实现 Sandbox Backend |
| 0017 | 沙箱网络 | 开放出网让 agent 自己装包，加固清单不动 |
| 0018 | worker 副本数 | 降为单副本，沙箱后端改全异步，进程存活靠看门狗 |

> **本节要点**：18 条 ADR 记录了每个关键取舍的理由；先读 0002、0004、0008、0013、0014 这五条。

## 10. 代码地图

代码全部在 `src/` 下。一个容易踩的坑先说：**`src/` 只是目录名，不是包名**——所有导入都从 `app.` 起算，不带 `src.` 前缀。平级的 `config.py`、`log.py`、`cursor.py` 也是裸导入。

| 目录 | 职责 | 一句话 |
|---|---|---|
| `app/api/` | 网关：路由、认证、SSE、错误结构 | 浏览器的唯一入口 |
| `app/run/` | run 生命周期：提交、执行、事件、审批、取消 | 主线所在 |
| `app/task/` | 任务队列封装 | Redis Stream + consumer group |
| `app/worker/` | 消费循环与运行时 | 不是 HTTP 服务 |
| `app/broker/` | 沙箱与 workspace 的管家 | 唯一碰 Docker 的进程 |
| `app/sandbox/` | 沙箱池、容器、路径、配额 | worker 侧对沙箱的视图 |
| `app/agent/` | 装配层：prompt / skill / MCP / 子 agent 拼成图 | 和 preset 别搞混 |
| `app/preset/` | 目录层：谁写了什么、共享给谁、审没审过 | 和 agent 别搞混 |
| `app/event/` | 平台事件模型与防腐层 | 前端契约的定义处 |
| `app/quota/` | 三道闸：限流、token 配额、并发上限 | 档位与依据在 `policy.py` |
| `app/store/` | 连接的建立、体检、关闭 | 不管表结构 |
| `app/thread/` 等 | 领域实体与 repository | 越权过滤长在这里 |
| `app/auth/` | 密码与会话 | 登录态在 Redis |
| `migration/` | 表结构（Alembic） | 16 个脚本，`create_all` 是禁语 |
| 根 `config.py` | 平台 Settings | 与 `agent/config.py` 不同 |

包名即职责，但有六组概念最容易搞混，读代码前先记下：

| 这个 | 不是那个 |
|---|---|
| `agent/` 装配层（把配置拼成可执行的图） | `preset/` 目录层（版本、共享、审核） |
| 根 `log.py` 进程日志（JSON 行，给运维） | `run/log.py` 事件日志（Redis Stream，给教师） |
| `run/submitter.py` 提交那一半（api 进程） | `run/executor.py` 执行那一半（worker 进程） |
| `threads` 表是会话存在的权威 | workspace 目录只是它的副产品 |
| `store/` 只管连接 | 表结构在 `migration/`，读写在各模块 repository |
| 根 `config.py` 平台设置 | `agent/config.py` 一次 run 内生效的配置 |

> **本节要点**：包名即职责；导入不带 `src.` 前缀；六组易混概念是前人踩过的坑。

## 11. 从这里开始读

**第一步，读文档。** `doc/01design/` 有九份设计文档：01 总体架构、05 运行时契约、06 数据设计、07 安全设计是最核心的四份；`doc/03plan/` 是 P0–P12 的分期计划与验收记录，读它能看到每个特性「为什么长成这样」的来龙去脉。

**第二步，走主线代码。** 按第 4 节的顺序读：`submitter.py` → `task/queue.py` → `worker/loop.py` → `run/executor.py` → `agent/factory.py` → `sandbox/` + `broker/` → `event/mapper.py` → `run/log.py` → `api/sse.py`。这一遍下来，骨架就立住了。

**第三步，用测试验证理解。** 这个仓库的测试是规格书级别的：

- 文件与模块一一对应：`src/test/run/executor_test.py` 对应 `src/app/run/executor.py`；
- 函数名即规格：`test_<场景>_<预期>`；
- `test/conftest.py` 要求**真 Postgres + 真 Redis**，起不来就整包跳过，绝不静默通过；api 测试里假的只有沙箱池和模型，api 与 broker 之间走真 HTTP；
- 想验证自己对某段代码的理解，直接跑 `cd src && uv run pytest test/run/executor_test.py -k <场景>`。

**第四步，按包分治。** 横切面（quota、auth、preset、usage）随时可以单独展开，每读一个包之前先看它对应的设计文档章节。

> **本节要点**：先文档后代码，先主线后分治，用测试当可执行规格书来验证理解。

## 12. 收尾：下一步与边界意识

读完本文，你手上应该有一张全景图、一条主线、一份文档地图。建议的下一步是：

1. 通读 `doc/01design/05runtime-design.md`（运行时契约，全链路细节都在里面）；
2. 读标注 ★ 的五条 ADR；
3. 跟着第 4 节走一遍代码主线，遇到疑问回来查文档。

最后留一个提醒：这个架构是为一两百人、单机、内网、非涉密数据设计的。当用户扩展到全院、需要跨主机、开始承载敏感数据、出现明确 SLA 要求时，架构前提就变了，必须重评——这些触发条件在 `01architecture.md` 第 7 节有完整清单。读代码时如果发现某个设计「看起来过度」或「看起来不够」，先想想它对应的前提，多半能自己找到答案。

> **本节要点**：架构为当前规模量身定做；前提变了就要重评，不要拿现状当教条。
