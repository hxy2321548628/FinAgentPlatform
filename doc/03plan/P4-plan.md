## 1. P4 的边界

**目标**（[架构 §11](../01design/01architecture.md)）：可观测性（OpenTelemetry）、MinIO 产物存储与 workspace 归档回收、成本看板。**验证标准原文：能定位单个 run 的完整 trace 与 token 花费。**

五期一句话：**P0 回答「agent 好不好用」，P1 回答「不可信代码跑在这台机器上安不安全」，P2 回答「这台机器上的东西挂了会怎样」，P3 回答「谁在用、能用多少、人能不能插手」，P4 回答「出了问题怎么查、花了多少钱、产物放哪」。**

### 1.1 与前四期最大的不同：这一期的未知是「到底需不需要」

[P1](./P1-plan.md) 与 [P2](./P2-plan.md) 写的是「没有未知，只有工作量」。[P3 §1.1](./P3-plan.md) 的未知是**参数**：审批范围、配额数值、限流阈值 —— 方案是定的，缺的是数据。

**P4 的未知是必要性本身。** 架构 §8.3 那一节至今整体是 `TODO`，它列的四项里，每一项都要先回答「在这个规模上真的需要吗」：

| 项 | 为什么要先问「需不需要」 |
|---|---|
| 链路追踪（OpenTelemetry） | 单机、进程只有五个、结构化日志已经带 `run_id`/`thread_id`/`user_id` 且能逐行 `jq`。一个 run 的过程现在**已经串得起来**，OTel 多给的是「每一段花了多少毫秒」。为这个引入 collector + 后端 + 全链路埋点，值不值 |
| 指标 | 活跃 run 数、队列积压这些，Postgres 与 Redis 各一条查询就有。是要上 Prometheus + Grafana，还是一个 `/admin/metrics` 端点就够 |
| 日志集中收集 | 架构自己写着「内网单机可能不需要 ELK，`docker logs` + loki 或直接文件轮转就够」 |
| 成本看板 | **没有前端**（[P3 §7.3](./P3-plan.md) 定案不做，本期仍不做）。看板做出来是一个返回 JSON 的端点，谁看 |

**这不是要砍掉 P4。** 排障能力与成本可见性都是上线前该有的。但 [P3 §8.7](./P3-plan.md) 刚刚给过一个教训：**`ANALYSIS_TOKEN` 的初值从一个样本外推，实测差了 61 倍。**同样的错误在这里的形态是「照着一份为大规模微服务写的可观测性清单，给一台内网单机装一整套」。所以 §7 的头号待决就是这个。

**定案（2026-08-08）：装全套（§7.1）。** 计划初稿倾向轻量方案，理由是日志已能串起一个 run；**定案时按内存重算，这个理由站不住**：

| | 估算内存 | 占沙箱可分配 48 GB 的比例 |
|---|---|---|
| OTel Collector + Tempo + Loki + Prometheus + Grafana | 2–3 GB | **约 1.5 个沙箱名额 / 24 个，6%** |

> **实测结果（2026-08-08，§8.8）：0.41 GB，比估算小 5–7 倍**，连四分之一个沙箱名额都占不到。那笔账因此更划算，但**当时的论证方式仍然是对的** —— 手上没有实测值时，按估算的上界决策是正确做法。这一条与 [P3 §8.7](./P3-plan.md) 的 `ANALYSIS_TOKEN` 差 61 倍不是同一回事：那边是拿一个样本外推，这边是保守取上界。

初稿写的「每 2 GB 就少一个沙箱」本身没错，但没把总量摆出来，读起来比实际代价大。**6% 的容量换完整排障能力是划算的**，而「日志能串起来」与「能看出每段花了多少毫秒」是两件事 —— 后者正是架构 §11 验证标准点名要的。**这个估算本身要在步骤五落地后实测**，见 §4 观察项。

## 2. 三处与上游文档不一致，本期定案

### 2.1 产物「302 跳预签名 URL」在内网无域名的前提下走不通，改由 nginx 直发

[架构 §5.7](../01design/01architecture.md) 写：产物走 **302 跳预签名 URL**，理由是「不由网关代理二进制流 —— 否则大文件下载会长时间占住网关的 worker，而网关还要同时扛所有 SSE 长连接」。

**理由成立，方案有前提问题。** 预签名 URL 的 host 必须是浏览器够得着的地址。而本平台[内网部署、无域名、直接用内网 IP](../01design/01architecture.md)，要让浏览器直连 MinIO 就得把 MinIO 端口暴露到内网 —— 多开一个对外面，且 MinIO 的地址会硬编码进签名，换 IP 就全失效。

**定案：nginx 上给产物单开一个 `location`，`proxy_pass` 到 MinIO，不经 api 进程。**

这不是推翻原文，是澄清它反对的对象。原文要保护的是 **FastAPI 的 worker**（数量少、还要扛 SSE 长连接），而不是 nginx —— nginx 代理大文件正是它的本职，它已经在扛所有 SSE 且配了 `proxy_read_timeout 3600s`。这样：

- api 进程碰不到二进制流，原意达成
- MinIO 不暴露端口，攻击面不变
- 换 IP 不影响，签名只在 nginx 与 MinIO 之间

代价：nginx 成为产物下载的带宽瓶颈。单机内网、产物几百 KB 量级（[架构 §6.5](../01design/01architecture.md) 实测典型 350KB），这个代价可以接受；真撞上再改回暴露端口也不影响上层。

### 2.2 产物 id 换形状会打断历史事件，端点兼容两种而不迁移事件

现在产物的身份是 `{thread_id}/{outputs 下的相对路径}`（`app/api/route/artifact.py` 已就地写明「等表建起来，这里换成表主键，端点形状不变」）。

**问题**：`run.finished` 事件的 `artifacts` 字段里存的是旧形状，而 `run_events` 保留 **180 天**（[架构 §6.5](../01design/01architecture.md)）。换成表主键之后，这半年内的历史事件全部指向一个新端点不认识的 id —— 症状是教师翻旧会话时图打不开，且**不报错，只是 404**。

**定案：端点同时接受两种形状，不迁移历史事件。**

- 含 `/` 的按旧形状解析（thread + 相对路径），查 `artifacts` 表反查 `s3_key`；查不到再回落到 workspace
- 不含 `/` 的按表主键查

**事件是不可变的日志，改它是错的方向** —— 一旦开了「回写历史事件」的口子，`run_events` 就不再是「当时发生了什么」的可信记录。兼容期跟着保留期走，180 天后旧形状自然消失，届时删掉回落分支。

### 2.3 workspace 归档回收：本期定案**不做**

[架构 §6.5](../01design/01architecture.md) 原方案是「归档到 MinIO 后删除本地副本，下次需要时拉回」，并写明「错的是它的前提眼下不存在」（没有 MinIO）。本期 MinIO 落地，前提就有了 —— **但收益仍然不成立**。

同一节自己的实测数据：

| 项 | 实测（2026-08-07，7 个真实会话） |
|---|---|
| 单会话占用 | 最大 408 KB，典型 ~350 KB |
| 与 5GB 配额的距离 | **四个数量级** |
| 按 100 教师 × 50 会话/年 推算 | 约 **2.5 GB/年** |

**为一年 2.5 GB 去建一套「归档 → 删本地 → 按需拉回」的机制，是明确的坏交易。** 拉回逻辑要处理：拉的时候沙箱在不在、拉到一半失败怎么办、拉回后什么时候再删、并发的两个 run 同时拉同一个会话。这些都是真实的失败模式，而它们换来的是几个 GB 的磁盘。

**定案：本期只把「产物」写进 MinIO（产物要长期留存、要能直发、要有 `s3_key`），workspace 本身不归档、不删、不拉回。** [架构 §6.5](../01design/01architecture.md) 已经定好的重新评估触发条件继续有效 —— 体检脚本连续报红，或单会话占用逼近配额成为常态。届时再单做，那时也才有真实的占用分布可依。

**这一条要回填架构 §6.5 与 §11**，把 P4 一行里的「workspace 归档回收」改成「产物存储」，两处不再打架。

## 4. 验收标准

与前四期同样的口径，**一条命令能跑完**。本期新增的判据进 `deploy/test/p4.sh`，P0–P3 的回归由既有脚本转调。

```bash
make all
docker compose -f deploy/compose.yml up -d

bash deploy/test/p4.sh                       # 本期若干条，转调 p3.sh 做回归
```

**通过条件**（八条全中才算完）。第 1 条是[架构 §11](../01design/01architecture.md) 给 P4 定的原文标准：

1. **能定位单个 run 的完整 trace 与 token 花费** —— 给一个 `run_id`，在 Grafana 里拿到它在网关 / worker / LLM / sandbox 各段的耗时，以及这次的 token 三元组。**「能定位」要落到一个具体页面上**，不能是「日志里都有，自己 grep」。
2. **产物从 MinIO 直发，api 进程碰不到字节** —— 下载一张产物图，`api` 容器不经手该字节流；抓一次请求确认 nginx 直发路径成立（§2.1）。
3. **旧形状的产物 id 仍然打得开** —— 用 P3 期留下的历史 `run.finished` 事件里的 id 请求产物，仍返回图而不是 404（§2.2）。
4. **产物列表不再偶发为空** —— [P3 §8.3](./P3-plan.md) 那条查清并修掉；**判据要先证明它原来会红**（拿修复前的代码跑复现脚本，必须复现）。
5. **成本看板答得出「谁花了多少」** —— `GET /admin/usage` 按用户与时间聚合，静态页打得开，且**管理员看得到用量、看不到会话内容**（[架构 §6.3](../01design/01architecture.md) 的边界不能被这个端点绕开）。
6. **告警真的会响** —— 把阈值调到必然触发，**确认飞书真收到那条消息**，再调回。没验过的通道与没有告警是一回事。
7. **`resumed` 改完之后语义对得上** —— 崩溃恢复那一程报 `true`，`queued` 起跑那一程报 `false`。这条可以复用 `p2.sh` ① 造出来的崩溃场景。
8. **P3 验收七条不回归**。

> **两条观察项（不设门槛）**：
>
> - 延续 [P3 §4](./P3-plan.md)：每次验收记一次真实分析的未命中 token。P3 已攒到八个样本，区间 5,199–318,768（[P3 §8.7](./P3-plan.md)）。**攒够之后回 `quota/policy.py` 校准初值**，那是这条唯一的目的。
> - **本期新增：可观测性那五个服务实际吃掉多少内存。** §1.1 的 2–3 GB 是估算，而沙箱并发上限直接由剩余内存决定（[架构 §4.4](../01design/01architecture.md)）。实测值要回填 §1.1 与架构 §4.4 的容量推算 —— **P3 刚证明过「从估算外推」会差多远**。

## 5. 任务分解

每步独立可验，未过不进下一步。**步骤零不是 MinIO** —— 见 §1.2 第 11 条。

| 步骤 | 内容 | 验证 |
|---|---|---|
| **零** | 查清并修掉「产物列表为空」的偶发红 | 复现脚本**在修复前必红**、修复后连跑 100 次全绿 |
| **一** | MinIO 起服务 + `artifacts` 表 + 写入路径按租户前缀 | 跑一次真实分析，产物同时落 MinIO 与表；`s3_key` 前缀正确 |
| **二** | 产物端点改 nginx 直发，兼容旧形状 id（§2.1、§2.2） | 验收 ②③ |
| **三** | `resumed` 语义改（§7.4）：`start()` 拆成两步条件更新 | 验收 ⑦ |
| **四** | 成本看板：`GET /admin/usage` + 单文件静态页（§7.5） | 验收 ⑤ |
| **五** | Prometheus + Grafana + 指标埋点 | 指标抓得到；**实测五个服务的内存占用**（§4 观察项） |
| **六** | OTel Collector + Tempo（后端 MinIO）+ 全链路埋点 | 验收 ① |

## 7. 待决事项（2026-08-08 全部关闭）

与 [P3 §7](./P3-plan.md) 同一个规矩：五项全部关闭才开工。

### 7.1 可观测性装多少 —— **定案：全套**

三条路：**A 全套**（OTel Collector + trace 后端 + Prometheus + Grafana）、**B 轻量**（只加 `GET /admin/metrics` + 日志里补 span 耗时）、**C 只做成本与用量**。

**选 A。** 决策过程记在 §1.1：初稿倾向 B，理由是「日志已能串起一个 run」；定案时按内存重算，全套约 2–3 GB，只占沙箱可分配容量的 6%（1.5 / 24 个名额）。**6% 换完整排障能力划算，而且「能串起来」与「能看出每段花多少毫秒」是两件事** —— 后者正是[架构 §11](../01design/01architecture.md) 验证标准点名要的，选 B 等于交付一半。

放弃 B 的代价：多五个服务要运维、要埋点。放弃 C 的代价：无。

### 7.2 后端选型 —— **定案：Tempo + Loki + Prometheus + Grafana，且 trace 与日志都以 MinIO 为后端**

§7.1 选 A 之后这一项就跟着定了：

| 用途 | 选型 | 存哪 |
|---|---|---|
| 采集 | OpenTelemetry Collector | — |
| trace | Tempo | **MinIO** |
| 日志 | Loki | **MinIO** |
| 指标 | Prometheus | 自带 TSDB（本地卷） |
| 看板与告警 | Grafana | — |

**关键是 trace 与日志都指向 MinIO**：本期第 1 项本来就要落 MinIO，让它同时当 Tempo 与 Loki 的对象存储，就不必再为这两样各切一块本地磁盘，保留期也统一由对象存储的生命周期规则管。**这条把步骤顺序钉死了：MinIO 必须排在 trace 与日志之前**（§5 的步骤一正是它）。

Prometheus 不走 MinIO —— 指标是小而密的时序数据，本地 TSDB 更合适，远程写入反而增加故障面。

**数据卷不得用匿名卷**（[架构 §8.5](../01design/01architecture.md)），与 Postgres 同一条规矩，Prometheus 与 MinIO 都适用。

### 7.3 告警投递 —— **定案：飞书机器人**

走 Grafana Alerting 的 webhook contact point 打到飞书自定义机器人。与 §7.1 选 A 天然接得上，不必另写投递代码。

**webhook 地址是凭据，进仓库根的 `.env`（`FEISHU_WEBHOOK_URL`），不入库**，模板加进 `.env.example`。业务侧不直接读，一律走 `pydantic_settings`；Grafana 侧由环境变量注入。

**验收要先证明它真会响**（§4 ⑥）：把阈值调到必然触发，确认飞书真收到，再调回。**没验过的告警通道与没有告警是一回事** —— 这正是[验收脚本自身失效](./P3-plan.md)那一类问题的告警版本。

### 7.4 `resumed` 的语义 —— **定案：改**

现在 `resumed = task.decisions is not None`（`run/executor.py`），只标「审批之后的续跑」，崩溃重投报 `false`。**改成「这不是第一次开跑」** —— 崩溃恢复与审批续跑，对前端的含义完全一样：别把已经显示的对话重置。

**改它的理由不是好看，是它现在是个 bug 的种子**：前端拿到 `resumed=false` 就会当成新一轮开跑。**前端未开工是改事件契约最便宜的时刻，也是最容易忘掉它的时刻。**

实现上要能区分「从 `queued` 起跑」与「重投接着跑」。`RunRepository.start()` 现在允许 `queued / running / waiting_approval` 三种前态转 `running`，拆成两步条件更新即可：先试 `queued → running`，命中即首次；未命中再试其余前态，命中即续跑。两步各自原子，没有竞态。

同步要改：事件契约文档（[架构 §5.2](../01design/01architecture.md)）、[ADR-0013](../01design/adr/0013-event-anticorruption-layer-v2-stream.md) 防腐层、以及 [P2 §7](./P2-plan.md) 里引用过这个字段的地方。

### 7.5 成本看板的形态 —— **定案：端点 + 单文件静态页**

`GET /admin/usage` 返回 JSON，另配一个**自包含的 HTML**（无构建、无框架，nginx 直接托管）。

**这是运维页，不是教师用的产品前端** —— 后者仍无期次（§1.4）。做这一页的理由：[架构 §8.3](../01design/01architecture.md) 说成本看板是「§3.1 成本可控的落地手段」，而**一个没人看的 JSON 端点落不了地**；「看板」这个词本身就要求有东西可看。

边界不变：**管理员看得到用量，看不到会话内容**（[架构 §6.3](../01design/01architecture.md)），这一页只呈现聚合数字，验收 ⑤ 单独验这条。

## 8. 实施记录

按 §5 的步骤逐条回填。**只记「实施时才知道的东西」** —— 计划里已经写过的不重复。

### 8.1 步骤零：「产物列表为空」的真因是两个时钟不同源（2026-08-08 关闭）

真因是**基准与判据用了两个不同的时钟**：

| | 谁读的 | 读的是什么 |
|---|---|---|
| 基准 `since_ns` | worker 进程，`time.time_ns()` | CLOCK_REALTIME，**细粒度**，纳秒即时值 |
| 判据 `st_mtime_ns` | 内核给 inode 打的时间戳 | **粗粒度时钟**，每个 tick 更新一次 |

粗粒度时钟落后细粒度时钟最多一个 tick，而 **NOHZ 下进程一空闲，它就停在上一次 tick 上不再被推进**。于是「先取基准、紧接着写产物」会得到一个 mtime **早于**基准的文件 —— 被判成「运行之前就有的」，静默漏掉，且没有任何报错。

**实测**（本机 `CONFIG_HZ=1000`、Linux 6.17）：

| 场景 | 漏掉 | 最负时间差 |
|---|---|---|
| 墙钟基准 | **30 / 1000（3.0%）** | −737,438 ns |
| 文件系统基准 | 0 / 1000 | +60,481 ns（全为正） |

**[P3 §8.3](./P3-plan.md) 那个「13,000 个样本、负差一次都没有」的探针没错，是场景造错了**：它在紧循环里连写 5,000 个文件，CPU 一直忙，tick 从不缺席，粗粒度时钟也就从不落后。真实路径里取基准之前有约 20 毫秒的 HTTP 往返空档 —— **偏差正是在那段空闲里张开的**。把探针的 `sleep` 从「取基准之后」挪到「取基准之前」，3‰ 的负差立刻出现。

这条给[「先验证验证代码」](./P3-plan.md)又添了一个形态：**探针不红不等于假说不成立，也可能是探针没造出要测的场景**。因此复现脚本 `deploy/test/artifact_flake.py` 把「墙钟那一轮必须红」也写成了判据 —— 它不红就报失败，而不是报通过。

**修法：基准也向文件系统要。** 新增 `SandboxBackend.artifact_mark()`，把 `outputs/` touch 一下再读它的 mtime；基准与判据从此出自同一个时钟。执行器不再读自己的墙钟，改经 `POST /threads/{id}/artifacts/mark` 向 broker 要 —— **只有 broker 那一侧碰得到宿主机的文件系统**，这一点与产物判定本来就在 broker 侧是同一个理由。代价是每个 run 多一次 HTTP 往返，相对几分钟的分析可以忽略。

判据仍是闭区间 `>=`，而且**现在非闭不可**：粗粒度时钟下，与基准同一个 tick 内写下的产物 mtime 与基准完全相等，用 `>` 会把它们全漏掉。

**验证**：复现脚本两轮判据都中；原来那两条偶发红的用例各连跑 100 轮全绿；`make all` 654 条全过。

### 8.2 步骤一：MinIO 落地与 `artifacts` 表

**三个实施时才定下来的取舍**：

**一、MinIO 客户端放在 broker 里**（§6 把这一条列成了 P1 的回归风险）。产物的字节躺在 broker 独占的 workspace 里，让 api 或 worker 来传就得先把字节经 HTTP 搬过去 —— 凭空多一跳，还得给它们开一条本来不需要的文件通路。**落表仍在 worker**：broker 至今一行 SQL 都不发，为一张它自己不查的表开一条库连接不划算。于是形成 `mark → collect → add` 三步：broker 传字节并交回元数据，worker 顺手落表。

**二、上传失败不升级成 run 失败。** 分析已经跑完了，字节也还在 workspace 里（§2.3 定案不删），仍按旧形状下得动 —— 为一次存储抖动扔掉几十分钟的分析与已经烧掉的 token 不划算。因此 `CollectedArtifact.s3_key` 可以为空，**空的那些不落表**：表里的每一行都必须指向一个真的对象，否则查出来的键下载不了，而那种 404 不指向原因。这与 §2.2 定好的「查不到再回落到 workspace」正好是同一条退路。失败记 `error` 而不是 `warning`，留给步骤七的告警收。

**三、无主的 run 不上传。** 租户前缀取自提交的人（`tenant/{user_id}/thread/{thread_id}/`），而 `RunTask.user_id` 在类型上仍可为空（P3 之前投进队列的任务）。**按某个默认前缀上传是错的** —— 那正是「越权面」这类问题最典型的来源。这种 run 记一条 warning 并报零产物。

**事件契约本期不动**：`run.finished` 里仍是旧形状 `{thread_id}/{相对路径}`。换成表主键要等步骤二把端点改成同时认两种形状，否则这中间产物就下不动了。

**顺手清掉的孤儿**：`RemoteWorkspace.artifact_since` 与 broker 的 `GET /threads/{id}/artifacts` 因 `collect` 取代而再无调用方，一并删除。`SandboxBackend.artifact_since` 留着 —— `collect` 内部还用它。

**验证**（2026-08-08，compose 全栈 + 一次真实分析）：

| 判据 | 实测 |
|---|---|
| run 跑完 | `succeeded` |
| 产物落表 | `s3_key = tenant/9cf9849d…/thread/737ab2d6…/index.png`，`mime=image/png`，`size=123650` |
| 前缀正确 | 与 `tenant/{user_id}/thread/{thread_id}/` 逐段对上 |
| 字节真在 MinIO 里 | `mc cat` 出来 123,650 字节，与 broker 从 workspace 直取的那份**逐字节等长** |
| 事件仍是旧形状 | `artifacts: ["737ab2d6…/index.png"]` |
| 门禁 | `make all` 679 条全过；MinIO 起来之后原本 skip 的 6 条产物用例全部真跑 |

**§4 观察项记一笔**：这次真实分析未命中 token **113,612**（cache 命中 75,264，输出 1,992）。P3 的八个样本区间是 5,199–318,768，这一个落在区间内。

**一个部署上的坑**：`mc ls local/artifact/tenant/{user_id}/` 列出来的路径是**相对于所给前缀**的（显示 `thread/…/index.png` 而不是完整键）。核对前缀时别把它当成「前缀没生成对」。

### 8.3 步骤二：直发走 `X-Accel-Redirect`，不是 302

§2.1 定了「nginx 直发」，但没说**怎么把鉴权与直发接起来**。302 跳到一个 nginx 上的产物 location 会留下一个谁拿到谁能下的 URL；而让 nginx 直接 `proxy_pass` 又等于绕开 P3 的隔离。

**定案：`X-Accel-Redirect`。** api 鉴权、解析标识、签一条预签名 URL，把 URL 削成只剩路径与查询串放进响应头，响应体留空；nginx 认这个头，自己去 MinIO 取字节发给浏览器。一次请求、一次鉴权，签名不进浏览器，`internal` 让外部打不进那条 location。

**内部路径前缀直接用桶名**（`/artifact/`）。这不是省事：预签名 URL 削掉 host 之后剩下的正好是 `/{桶}/{键}?{签名}`，nginx 按桶名匹配就能**原样**转给 MinIO —— 一个字符都不改写。改写就要经过「解码 → 重新编码」，而签名是按编码后的路径算的，两边编码规则只要差一点签名就对不上。代价是 `nginx.conf` 的 location 与 `.env` 的 `MINIO_BUCKET` 必须一致，两处都写了注释。

**这条风险是实测掉的，不是推理掉的**：验收时特意让 agent 存一张**中文文件名**的图（`行业波动率.png`），全程 200。

**开发机没有 nginx**，`X-Accel-Redirect` 在那里只会让浏览器收到一个空响应。因此加了 `ARTIFACT_DIRECT_SEND`，默认 `false`（api 自己从对象存储取回来转发），compose 里置 `true`。

**事件契约本期换形状**：进了对象存储的报 `artifacts` 表主键，没进去的仍报旧形状。端点按含不含 `/` 分辨 —— 两种形状因此各自都有真实来源，新分支不是死代码。

**验证**（2026-08-08，compose 全栈 + 四次真实分析）：

| 判据 | 实测 |
|---|---|
| ② api 不经手字节 | 绕过 nginx 直接问 api：**响应体 0 字节** + `X-Accel-Redirect: /artifact/tenant/…?X-Amz-Algorithm=…`；同一个产物经 nginx 是 19,468 字节的 PNG |
| ② 直发路径成立 | 把 workspace 那份**挪走**之后仍下得动，且与挪走前逐字节一致 —— 字节确实来自 MinIO，不是回落 |
| ② 外部打不进 | `GET /artifact/…` 直接请求 → **404**（`internal` 生效） |
| 中文文件名 | `行业波动率.png` 新旧两种 id 都是 200，118,755 字节 |
| ③ 旧形状仍打得开 | 见下 |
| 门禁 | `make all` 693 条全过 |

**③ 的判据换过一次，因为原判据测不到东西。** 原计划是「拿 P3 期留下的历史事件里的 id 去请求」，实测 **404**。查下去发现**不是回落逻辑坏了**：那些 P3 期的 workspace 目录早被清理过，`outputs/` 已经不存在 —— 字节两边都没有，404 是**正确答案**。机器上没有真实遗留可测。

改成**重建那个条件**：跑一次真实分析，然后删掉 `artifacts` 表里的行，只留 workspace 里的字节 —— 那正是 P3 期产物的形态。并且把判据做成可证伪的：

```
表里有行            → 200；把 workspace 藏起来仍 200   （走的是 MinIO）
删掉表行 + 藏 workspace → 404                            （判据会红）
删掉表行 + 留 workspace → 200，且与走 MinIO 那次逐字节一致（回落成立）
```

中间那一行是关键：**没有它，「200」证明不了走的是回落分支**。这与[「先验证验证代码」](./P3-plan.md)是同一件事 —— 一条永远绿的判据等于没有判据。

### 8.4 步骤三：`resumed` 的两个来源，缺一不可

§7.4 给的实现是「`start()` 拆成两步条件更新：先试 `queued → running`，命中即首次；未命中再试其余前态，命中即续跑」。**这只覆盖了一半。**

审批之后 `RunRepository.resume()` 把状态放回 **`queued`**，续跑那一程因此走的是第一步、报「首次」—— 而它明明是续跑。光看状态区分不出它。

**定案：两个来源取并集。**

```python
resumed = task.decisions is not None or start is RunStart.RESUMED
```

| 来源 | 认得出的场景 | 认不出的 |
|---|---|---|
| 任务带决策 | 审批之后的续跑 | 崩溃重投（那一程不带决策）|
| 前态是 `running` / `waiting_approval` | 崩溃或超时之后的重投 | 审批续跑（`resume()` 已把状态放回 `queued`）|

`start()` 的返回值从 `bool` 换成 `RunStart` 三值枚举（`FIRST` / `RESUMED` / `REFUSED`）—— 一句 `UPDATE ... WHERE status IN (...)` 只回答「改了几行」，答不出「命中的是哪个前态」。两步各自原子；中间那一刻状态再变，也只会让第二步落空，不会写坏。

**验证**（2026-08-08，compose 全栈 + 一次真实崩溃）：等第一条 `tool_result` 出现再 `kill -9` worker，run 最终 `succeeded`，两条 `run.started` 的 `resumed` 依次是 **`[false, true]`**。

**判据先证明「真崩到了」**：`run.started` 少于两条就记未验、不许记通过 —— 那说明 kill 没生效或重投撞上了终态守卫，这一条什么都没验着。这正是 [P2 §① 那条判据两头都会骗人](./P3-plan.md)的教训。

**同步改了三处**：架构 §5.2 的事件契约表（`run.started` 补上 `resumed` 及其新含义，`run.finished` 的 `artifacts` 说明两种形状）、`deploy/test/p2.sh` ① 那段解释「假红」成因的注释。[ADR-0013](../01design/adr/0013-event-anticorruption-layer-v2-stream.md) 全文不涉及这个字段，不必改。

### 8.5 步骤四：账本与闸门分开放

用量聚合**没有塞进 `quota/usage.py`**，而是新开了 `report/usage.py`：

| | `quota/usage.py` | `report/usage.py` |
|---|---|---|
| 回答 | 这个人还能不能再跑一个 | 钱花在谁身上 |
| 过滤 | **永远带 `user_id`** | 跨所有用户聚合 |
| 角色 | 闸门 | 账本 |

那个类刻意不提供「不带 user 也能查」的入口 —— 多租户最常见的越权来源就是某个接口忘了加 where 条件。把账本的查询塞进去，等于亲手在那儿开一条旁路，而**旁路一旦开出来就很难再收回去**。

**三个实现上的取舍**：

- **统计所有 run，不只是成功的。** 失败与取消的一样烧了 token，只算成功的会系统性低估真实成本。
- **按未命中 token 排序，不按总数。** cache 命中那部分几乎不要钱（[架构 §6.4](../01design/01architecture.md)）。排序本身就是答案 —— 看板要回答「谁花得最多」，让人自己在一屏数字里找不算回答。
- **没有 run 的那天不占一行。** 补零是呈现层的事，报表不该假装那天有过记录。

**`require_admin` 给 403 而不是 404**，与产物端点的 404 不矛盾：越权访问**他人的资源**必须伪装成 404（403 等于确认了资源存在，可拿来探测别人有哪些会话），而「你的角色不够」不泄露任何东西 —— 管理端点存不存在本来就写在 `/docs` 上。

**验证**（2026-08-08，compose 全栈）：

| 判据 | 实测 |
|---|---|
| 静态页打得开 | `GET /usage.html` → 200 `text/html` |
| 教师打不开 | 403，`code=FORBIDDEN` |
| 未登录打不开 | 401 |
| 答得出「谁花了多少」 | 42 个用户、3 天，按未命中降序，头名 314,524 |
| **账对得上** | 端点各用户未命中之和 = 直接查库 = **1,343,879** |
| **看不到会话内容** | 响应正文里既没有 `title`/`content`/`thread_id`/`run_id` 字段，也搜不到库里任何一条真实会话标识 |
| 字段名对得上 | 页面用到的 11 个字段与端点实际返回的键逐一核对，全中 |

**最后一条是刻意加的。** 「页面 200」证明不了「页面显示得出东西」—— 字段名对不上时页面是一片空白，而 curl 看到的仍是 200。这是[「先验证验证代码」](./P3-plan.md)在前端侧的形态。

**这一页是运维页，不是教师用的产品前端** —— 后者仍无期次（§1.4 的第一大债没有被这一步偿还）。

### 8.6 步骤五：Prometheus + Grafana + 指标埋点

**五个指标分别只有一个进程答得出，因此抓取端点做了三个**，谁都不去替别人回答：

| 进程 | 端点 | 它独有的观测位置 |
|---|---|---|
| api | `GET /metrics`（8000） | Postgres 与 Redis 里的平台状态：run 各态计数、队列积压、当日 token |
| broker | `GET /metrics`（8100） | 唯一持有 `docker.sock`，因此只有它数得出沙箱容器与内存 |
| worker | 9101（`WORKER_METRIC_PORT`） | 唯一调模型，因此只有它量得到一次 LLM 调用有多慢、失不失败 |

**worker 那个端口是它唯一监听的端口** —— 它不是 HTTP 服务。端口起不来只记 error 不拦启动：worker 的职责是把分析跑完，为一个观测端口拒绝启动等于把观测手段变成可用性风险。这不是静默降级，抓不到的那一刻 Prometheus 的 `up` 就是 0。

**绝大多数指标是「现查」的 gauge，每次抓取现建一个注册表填完就扔。** 不在进程里攒计数器的理由不是省事：api 一个进程、worker 两个副本，任何攒着的数都要在 PromQL 那一侧 `sum()` 才对得上，而漏了 `sum()` 不报错，只给出一个偏小的数。只有 LLM 那两个真正累积的指标是长生命周期的 —— 直方图的语义本就要求跨请求存活。

**四处「实施时才知道」的东西**：

- **`/metrics` 不要求登录，挡它的是 nginx 一行 `return 404`。** Prometheus 没有会话，给它发一份长期凭据只是把同一个问题换个地方放。但响应里带着**用户名与他今天烧掉的 token** —— 与成本看板同一份数据，而那一侧是要管理员身份的。Prometheus 在 compose 网络里直连 `api:8000`，走不到 nginx。
- **worker 有两个副本，抓取配置必须走 DNS 发现。** 写死一个地址不会报错，只会让 LLM 调用量看起来正好少一半。实测 `dns_sd_configs` 把 `172.19.0.10` 与 `.11` 两个都发现出来了。
- **`XPENDING` 在 consumer group 还没建出来时抛 `NOGROUP`。** 全新部署到第一条任务投进来之间就是这个状态 —— 不接住的话，监控恰好在最该看它的那一段（刚部署完）是 500。改成答 0，那也确实是那时的实情。
- **Grafana 的 provisioning 子目录名写死是复数**（`datasources` / `dashboards`）。按项目的单数命名规矩写成单数时，它**一声不响地什么都不加载**：容器起得来、日志无异常、界面打得开，只是数据源和看板一个都没有。这条规矩管的是我们自己的文件，不管三方约定的查找路径。

**验证**（2026-08-08，compose 全栈）：

| 判据 | 实测 |
|---|---|
| 抓取目标全 up | 5 个：api / broker / prometheus / **worker ×2** |
| 边界成立 | 经 nginx 请求 `/metrics` → **404**；容器网络内直连 `api:8000/metrics` → 200 |
| 八块面板都取得到数 | 逐条把面板的 PromQL 打到 Prometheus 上跑，9 个查询全部返回非空 |
| 看板真能取到数 | 经 **Grafana 自己的数据源代理**查一次 `zuel_run`，`success` 且有值 —— 「看板存在」证明不了「数据源 uid 对得上」 |
| **LLM 回调真的挂上了** | 跑两次真实分析后 `zuel_llm_call_second_count{outcome="ok"}=2 → 4`，p50 2.14s / p95 4.71s |

**倒数第二条与第三条的区别值得单记。** 面板查询能在 Prometheus 上跑通，与看板能在 Grafana 里显示出来，是两件事 —— 中间隔着一个数据源 uid。这与 §8.5 那条「页面 200 证明不了页面显示得出东西」是同一个形态。

**最后一条是这一步唯一没法靠单测验的东西**：回调处理器本身有五条用例（含并发交错与孤儿结束事件），但「它有没有被挂到模型上」只有真跑一次模型才知道 —— 挂漏了不会报错，只会让那两条曲线永远是平的。

#### 8.6.1 §4 观察项：内存实测（部分）

**§1.1 估算全套 2–3 GB。目前起了五个中的两个：**

| 服务 | 实测常驻 |
|---|---|
| Prometheus | **51 MiB** |
| Grafana | **166 MiB** |
| 小计 | **217 MiB** |

**比估算小一个数量级。** 估算那个数是照着「为大规模微服务写的可观测性清单」来的，而这台机器上 Prometheus 的 TSDB 里只有五个抓取目标、几十条序列。**剩下三个（OTel Collector / Tempo / Loki）在步骤六、七起来之后补齐，届时回填 §1.1 与架构 §4.4。**

顺带记两个别处看不到的数（同一次实测）：

- **平台自身**：api 132 MiB、broker 119 MiB、worker 各 ~165 MiB、nginx 13 MiB、Postgres 43 MiB、Redis 19 MiB、MinIO 228 MiB。

#### 8.6.2 指标顺手照出来的一件事

抓取一上线，`zuel_run` 第一屏就是 **queued 93、running 49、waiting_approval 1**。这些是 P0–P3 历次验收里 worker 被 kill 之后留下的、再没有人接手的 run —— 它们一直躺在库里，只是**在此之前没有任何一个地方会把这个数显示出来**。

不在本期范围内修（没有「僵尸 run 清理」这一项），记在这里是因为它正好说明了这一步的价值：**这个数不是新产生的，是一直存在却看不见的。**

### 8.7 步骤六：OTel Collector + Tempo，一个 run 的完整 trace

**整条链路上只有一段要手接。** 其余全是探针自动完成的：

| 跨越 | 怎么串上的 |
|---|---|
| 浏览器 → api | FastAPI 探针开根 span |
| api → broker、worker → broker | httpx 探针把 traceparent 放进请求头，对面的 FastAPI 探针取出来 |
| **api → worker** | **手接**：中间隔着一条 Redis 队列，没有请求头可放 |

第三条是 `telemetry/context.py` 存在的全部理由：把 W3C 的 `traceparent` 塞进 `RunTask` 带过去。**漏了它不会报错**，只会让每个 run 断成互不相干的两条 trace —— 而验收 ① 要的「一个 run 的完整耗时」正好落在断口上。

**四处「实施时才知道」的东西**：

- **探针要分两步装。** `instrument()` 只挂中间件，必须在应用开始服务**之前**调用（Starlette 的中间件栈一旦建起来就加不进去）；而接后端要读配置，只能在 lifespan 里。分不开的话就得在 import 时读 `Settings` —— 而 CI 没有 `.env`，那会让整个模块 import 即失败。没配后端时探针照样在，span 落到 OTel 的空实现上，几乎不要钱。
- **ASGI 探针默认给每次 `receive` / `send` 各开一个 span**，一次请求从 1 个变 4 个。SSE 那条更夸张：一个几十分钟的事件流每推一个事件就多一个 span。`exclude_spans=["receive","send"]` 关掉 —— 不关的话要找的那条 trace 会被自己的噪声埋掉。
- **指标与追踪各挂一个回调，不合成一个。** 两者对 LLM 调用的失效方式完全不同：指标丢一个样本没人看得出来，trace 少一段则整条链路对不上。
- **LLM 的 span 不能做成「当前 span」**（用 `start_span` 而不是 `start_as_current_span`）：一次分析里多轮调用是交错的，而「当前 span」只有一个 —— 互相顶替的话，后开的会认前一个当父，时间轴上就成了一串莫名其妙的嵌套。

**终态结论钉在 `_emit` 这一个漏斗里**，不在七八个终态分支里逐个写。取的是「当前 span」而不是把 span 传下去 —— 逐处传等于让每一处都记得这件事，而漏一处不报错，只会让那条 trace 少一半信息。

#### 8.7.1 一条测试自己会假过，被改掉了

第一版写了「worker → broker 那一跳在同一条 trace 里」，用来证明 httpx 探针生效。**它证明不了。** 那套夹具里 broker 与 worker 同进程同任务，上下文靠 `contextvars` 就传过去了 —— 把 httpx 探针整个拆掉，那条断言照样绿。

改成只声称它能证明的事（「broker 的应用挂上了探针」），**跨进程那一半明确交给 compose 全栈去验**。这与[「先验证验证代码」](./P3-plan.md)是同一件事：一条不会红的断言比没有断言更坏，因为它占着「已验证」的位置。

队列那一跳则相反 —— worker 的主循环跑在自己的任务里，上下文是夹具建立时那一份，**同进程并不会让它假过**。拿掉 `trace=carry()` 实测立刻变红。

#### 8.7.2 一条偶发红，真因是 span 比事件晚收尾

`test_the_run_id_is_searchable_on_the_worker_span` 八次里红三次，报的是「一个 `run.execute` 都没有」。

真因：**`run.execute` 是在终态事件发出去之后才结束的**（`with` 块还要退栈、归还沙箱），而 `drain()` 读到终态就返回了，两者差着几百微秒。断言跑在中间那一瞬。改成轮询等它收尾。

第一次猜的是「上一条用例的 span 漏进了这一条的窗口」，据此改了过滤方式 —— 没用。**打印出实际数量才看见是 0 而不是 2**，方向正好相反。[这条教训 P3 记过一次](./P3-plan.md)。

#### 8.7.3 验收 ①（2026-08-08，compose 全栈，真实分析）

给 `run_id = 0d7cf087…`，在 Tempo 里检索 `{ .zuel.run_id = "…" }`，拿到一条跨三个服务的 trace：

| 服务 | span | 耗时 |
|---|---|---|
| zuel-api | `POST /api/threads/{thread_id}/runs` | 15.1 ms |
| zuel-worker | `run.execute` | **6317.1 ms** |
| zuel-broker | `POST /threads/{thread_id}/sandbox` | 163.8 ms |
| zuel-worker | `llm.call` | 2573.1 ms |
| zuel-broker | `POST /threads/{thread_id}/tool/execute` | 73.2 ms |
| zuel-worker | `llm.call` | 3299.5 ms |
| zuel-broker | `POST /threads/{thread_id}/artifacts/collect` | 1.7 ms |
| zuel-broker | `DELETE /threads/{thread_id}/sandbox` | 0.9 ms |

`run.execute` 上的属性：`zuel.run_id` / `zuel.thread_id` / `zuel.user_id` / `zuel.status=run.finished` / `zuel.resumed=False` / **`zuel.token.input_cache_read=5888`、`input_uncached=165`、`output=234`** —— 与那次 `run.finished` 事件里的三元组逐位相同。

**验收 ① 通过。** 网关 / worker / LLM / sandbox 四段耗时齐全，token 三元组在同一个 span 上。

### 8.8 步骤七：Loki + Grafana Alerting → 飞书

**日志走 OTLP 从进程直接发出来，不去扒容器的 stdout。** 扒 stdout 要么给采集器挂 `/var/lib/docker/containers`（宿主机 root 才读得动，等于开一道本不需要的口子），要么装 docker 的日志驱动插件。这些日志本来就是这三个进程自己产生的，直接发更短，而且**顺带把 trace 与日志接上了** —— OTel 的 handler 会把当前 span 的 `trace_id` 写进每条日志。stdout 那一路原样保留：`docker logs` 照常看得到，Loki 挂了也不影响排障。

**三处「实施时才知道」的东西**：

- **`contextvars` 里的 `run_id` 到不了 Loki。** 那三个值由 JSON 格式化器在渲染那一刻现取，而 OTLP 这条路根本不经过格式化器 —— 它读的是记录本身的属性。症状是「stdout 上有 `run_id`，Loki 里没有」，而 Loki 里没有就等于按 run 过滤不出东西。补了一个 `logging.Filter` 把它们抄到记录上。
- **Loki 的 S3 端点要带协议前缀，Tempo 不要。** Tempo 收 `host:port`，Loki 3.x 换了 AWS SDK 之后要完整 URI，给 `minio:9000` 会以「Custom endpoint was not a valid URI」起不来。两处写法不一致是三方约定，不是笔误 —— 已在两个配置文件里各自注明。
- **改了挂载进容器的配置文件，`docker compose up -d` 不会重启那个容器。** compose 只比对服务定义，不看挂载文件的内容。给 collector 加了日志管道之后它照旧跑着老配置，症状是 api 侧一直报 `Failed to export logs batch code: 404` —— 而那个 404 指向的是「collector 上没有 /v1/logs 这条路由」，不指向「配置没生效」。要显式 `restart`。

#### 8.8.1 验收 ⑥：告警真的会响（2026-08-08）

**判据分三层，缺一层都不足以说「验过了」**：

| 层 | 做法 | 实测 |
|---|---|---|
| 1. 飞书认不认这个正文 | 把 Grafana 将要发的正文原样 POST 到 webhook | `{"code":0,"msg":"success"}` |
| 2. **判据分得开对错** | 换成 Grafana 的**默认**正文再 POST 一次 | `{"code":19002,"msg":"params error, msg_type need"}` |
| 3. 规则真的触发并投递出去 | 把「队列积压不消」的 `for` 临时调到 `0s` | 规则 `state=firing`；接收器 `lastNotifyAttempt=10:23:52`、耗时 `466ms`、**无 error**。验完调回 `15m` |

**第 2 层是这条验收的关键。** 飞书对形状不对的正文回的是 **HTTP 200 加一个业务错误码** —— 也就是说，用默认正文的话 Grafana 会认为发成功了，而群里什么都不会出现。**这正是 §7.3 说的「没验过的通道与没有告警是一回事」最具体的形态**：不去读飞书的业务码，前两层都是绿的。因此 contact point 里必须写自定义 payload，把正文套成飞书要的 `{"msg_type":"text","content":{"text":"…"}}`。

**触发用的是真实条件，不是造出来的**：库里躺着 93 个 `queued` 的历史 run（§8.6.2 那一批），本来就超过阈值 10。临时调的只是 `for`（等多久才报），不是阈值本身。

**这一条我这边验到的是「Grafana 成功投递、飞书 API 回 code 0」**。群里那条消息长什么样、是不是发到了对的群，要你自己看一眼 —— 那是我够不着的最后一格。

#### 8.8.2 四条告警规则

选择标准只有一个：**对应「教师会直接感受到的故障」**。一条没人会因此做任何事的告警，只会训练大家忽略这个群。

| 规则 | 判据 | 等多久 | 教师那边的感受 |
|---|---|---|---|
| 有进程抓不到了 | `up < 1` | 2m | 平台整个不响应，或分析永远停在排队 |
| 模型调用失败率偏高 | 近 15 分钟失败率 > 20% | 5m | 提交的分析大批失败 |
| 队列积压不消 | `queued > 10` | 15m | 提交了但迟迟不开跑 |
| 沙箱名额快用完了 | 容器数 > 18 | 10m | 新分析开始排队 |

**阈值都是初值，写得偏松。** [P3 §8.7](./P3-plan.md) 刚给过教训 —— 攒够真实运行数据再收紧，不要凭感觉调。

「模型调用失败率」那条的分子套了 `or vector(0)`：一次失败都没发生过时那条序列**根本不存在**，而 PromQL 里「空 / 数」等于空 —— 不套的话这条规则永远不成立，是一条配了但绝不会响的告警。§8.6 的看板面板踩的是同一个坑。
