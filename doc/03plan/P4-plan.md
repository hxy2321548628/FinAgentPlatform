## 1. P4 的边界

**目标**（[架构 §11](../01design/01architecture.md)）：可观测性（OpenTelemetry）、MinIO 产物存储与 workspace 归档回收、成本看板。**验证标准原文：能定位单个 run 的完整 trace 与 token 花费。**

五期一句话：**P0 回答「agent 好不好用」，P1 回答「不可信代码跑在这台机器上安不安全」，P2 回答「这台机器上的东西挂了会怎样」，P3 回答「谁在用、能用多少、人能不能插手」，P4 回答「出了问题怎么查、花了多少钱、产物放哪」。**

### 1.1 与前四期最大的不同：这一期的未知是「到底需不需要」

[P1](./P1-plan.md) 与 [P2](./P2-plan.md) 写的是「没有未知，只有工作量」。[P3 §1.1](./P3-plan.md) 的未知是**参数**：审批范围、配额数值、限流阈值 —— 方案是定的，缺的是数据。

**P4 的未知是必要性本身。** 架构 §8.3 那一节至今整体是 `TODO`，它列的四项里，每一项都要先回答「在这个规模上真的需要吗」：

| 项 | 为什么要先问「需不需要」 |
|---|---|
| 链路追踪（OpenTelemetry） | 单机、进程只有五个、结构化日志已经带 `run_id`/`thread_id`/`user_id` 且能逐行 `jq`。一个 run 的过程现在**已经串得起来**，OTel 多给的是「每一段花了多少毫秒」。为这个引入 collector + 后端 + 全链路埋点，值不值 |
| 指标 | 活跃 run 数、队列积压这些，Postgres 与 Redis 各一条查询就有。是要上 Prometheus + Grafana，还是一个 `/admin/metrics` 端点就够 |
| 日志集中收集 | 架构自己写着「内网单机可能不需要 ELK，`docker logs` + loki 或直接文件轮转就够」 |
| 成本看板 | **没有前端**（[P3 §7.3](./P3-plan.md) 定案不做，本期仍不做）。看板做出来是一个返回 JSON 的端点，谁看 |

**这不是要砍掉 P4。** 排障能力与成本可见性都是上线前该有的。但 [P3 §8.7](./P3-plan.md) 刚刚给过一个教训：**`ANALYSIS_TOKEN` 的初值从一个样本外推，实测差了 61 倍。**同样的错误在这里的形态是「照着一份为大规模微服务写的可观测性清单，给一台内网单机装一整套」。所以 §7 的头号待决就是这个，不关掉不开工。

## 2. 三处与上游文档不一致，本期定案

### 2.1 产物「302 跳预签名 URL」在内网无域名的前提下走不通，改由 nginx 直发

[架构 §5.7](../01design/01architecture.md) 写：产物走 **302 跳预签名 URL**，理由是「不由网关代理二进制流 —— 否则大文件下载会长时间占住网关的 worker，而网关还要同时扛所有 SSE 长连接」。

**理由成立，方案有前提问题。** 预签名 URL 的 host 必须是浏览器够得着的地址。而本平台[内网部署、无域名、直接用内网 IP](../01design/01architecture.md)，要让浏览器直连 MinIO 就得把 MinIO 端口暴露到内网 —— 多开一个对外面，且 MinIO 的地址会硬编码进签名，换 IP 就全失效。

**定案：nginx 上给产物单开一个 `location`，`proxy_pass` 到 MinIO，不经 api 进程。**

这不是推翻原文，是澄清它反对的对象。原文要保护的是 **FastAPI 的 worker**（数量少、还要扛 SSE 长连接），而不是 nginx —— nginx 代理大文件正是它的本职，它已经在扛所有 SSE 且配了 `proxy_read_timeout 3600s`。这样：

- api 进程碰不到二进制流，原意达成
- MinIO 不暴露端口，攻击面不变
- 换 IP 不影响，签名只在 nginx 与 MinIO 之间

代价：nginx 成为产物下载的带宽瓶颈。单机内网、产物几百 KB 量级（[架构 §6.5](../01design/01architecture.md) 实测典型 350KB），这个代价可以接受；真撞上再改回暴露端口也不影响上层。

### 2.2 产物 id 换形状会打断历史事件，端点兼容两种而不迁移事件

现在产物的身份是 `{thread_id}/{outputs 下的相对路径}`（`app/api/route/artifact.py` 已就地写明「等表建起来，这里换成表主键，端点形状不变」）。

**问题**：`run.finished` 事件的 `artifacts` 字段里存的是旧形状，而 `run_events` 保留 **180 天**（[架构 §6.5](../01design/01architecture.md)）。换成表主键之后，这半年内的历史事件全部指向一个新端点不认识的 id —— 症状是教师翻旧会话时图打不开，且**不报错，只是 404**。

**定案：端点同时接受两种形状，不迁移历史事件。**

- 含 `/` 的按旧形状解析（thread + 相对路径），查 `artifacts` 表反查 `s3_key`；查不到再回落到 workspace
- 不含 `/` 的按表主键查

**事件是不可变的日志，改它是错的方向** —— 一旦开了「回写历史事件」的口子，`run_events` 就不再是「当时发生了什么」的可信记录。兼容期跟着保留期走，180 天后旧形状自然消失，届时删掉回落分支。

### 2.3 workspace 归档回收：本期定案**不做**

[架构 §6.5](../01design/01architecture.md) 原方案是「归档到 MinIO 后删除本地副本，下次需要时拉回」，并写明「错的是它的前提眼下不存在」（没有 MinIO）。本期 MinIO 落地，前提就有了 —— **但收益仍然不成立**。

同一节自己的实测数据：

| 项 | 实测（2026-08-07，7 个真实会话） |
|---|---|
| 单会话占用 | 最大 408 KB，典型 ~350 KB |
| 与 5GB 配额的距离 | **四个数量级** |
| 按 100 教师 × 50 会话/年 推算 | 约 **2.5 GB/年** |

**为一年 2.5 GB 去建一套「归档 → 删本地 → 按需拉回」的机制，是明确的坏交易。** 拉回逻辑要处理：拉的时候沙箱在不在、拉到一半失败怎么办、拉回后什么时候再删、并发的两个 run 同时拉同一个会话。这些都是真实的失败模式，而它们换来的是几个 GB 的磁盘。

**定案：本期只把「产物」写进 MinIO（产物要长期留存、要能直发、要有 `s3_key`），workspace 本身不归档、不删、不拉回。** [架构 §6.5](../01design/01architecture.md) 已经定好的重新评估触发条件继续有效 —— 体检脚本连续报红，或单会话占用逼近配额成为常态。届时再单做，那时也才有真实的占用分布可依。

**这一条要回填架构 §6.5 与 §11**，把 P4 一行里的「workspace 归档回收」改成「产物存储」，两处不再打架。

## 4. 验收标准

与前四期同样的口径，**一条命令能跑完**。本期新增的判据进 `deploy/test/p4.sh`，P0–P3 的回归由既有脚本转调。

```bash
make all
docker compose -f deploy/compose.yml up -d

bash deploy/test/p4.sh                       # 本期若干条，转调 p3.sh 做回归
```

**通过条件**（草稿，随 §7 定案调整）。第 1 条是[架构 §11](../01design/01architecture.md) 给 P4 定的原文标准：

1. **能定位单个 run 的完整 trace 与 token 花费** —— 给一个 `run_id`，能拿到它在网关 / worker / LLM / sandbox 各段的耗时，以及这次的 token 三元组。**「能定位」要落到一条具体命令或一个具体页面上**，不能是「日志里都有，自己 grep」。
2. **产物从 MinIO 直发，api 进程碰不到字节** —— 下载一张产物图，`api` 容器的日志里不出现该字节流；抓一次请求确认 302 或 nginx 直发路径成立。
3. **旧形状的产物 id 仍然打得开** —— 用 P3 期留下的历史 `run.finished` 事件里的 id 请求产物，仍返回图而不是 404（§2.2）。
4. **产物列表不再偶发为空** —— [P3 §8.3](./P3-plan.md) 那条查清并修掉；判据要能证明它**原来会红**（拿修复前的代码跑一遍复现脚本）。
5. **成本看板答得出「谁花了多少」** —— `GET /admin/usage` 按用户与时间聚合，且**管理员看得到用量、看不到会话内容**（[架构 §6.3](../01design/01architecture.md) 的边界不能被这个端点绕开）。
6. **告警真的会响** —— 制造一次 workspace 超阈值，确认告警投递到位。**这条要先验证验证代码**：把阈值调到必然触发，确认它真报，再调回。
7. **P3 验收七条不回归**。

> **观察项（不设门槛）**：延续 [P3 §4](./P3-plan.md) 那条 —— 每次验收跑完记一次真实分析的未命中 token。P3 已攒到八个样本，区间 5,199–318,768（[P3 §8.7](./P3-plan.md)）。本期继续攒，**攒够之后回 `quota/policy.py` 校准初值**，那是这条观察项唯一的目的。

## 7. 待决事项

**五项全部关闭前不开工**，与 [P3 §7](./P3-plan.md) 同一个规矩。

### 7.1 可观测性到底装多少（头号问题）

单机、五个进程、几十并发、日志已经带 `run_id` 且逐行可 `jq`。三条路可选：

| 方案 | 代价 | 拿到什么 |
|---|---|---|
| **A. 全套** OTel collector + Tempo/Jaeger + Prometheus + Grafana | 四个新服务、全链路埋点、内存与运维开销 | 教科书式的可观测性 |
| **B. 轻量** 只加 `GET /admin/metrics`（Prometheus 文本格式）+ 在现有日志里补 span 耗时字段 | 几百行 | 指标可抓、耗时可查，但没有 trace 视图 |
| **C. 只做成本与用量**，排障继续靠结构化日志 | 最小 | 满足架构 §11 验证标准的一半 |

**倾向 B**，理由是架构 §8.3 自己写着「内网单机可能不需要 ELK」，同一条逻辑适用于 trace。但这要正式定，因为验证标准原文点名了「完整 trace」。

### 7.2 指标与日志的后端选型

若 §7.1 选 A 或 B，还要定：指标存哪（Prometheus 自带 TSDB 够不够）、日志集中收集用 loki 还是文件轮转、看板用 Grafana 还是自绘。**这三项的共同约束是内存** —— [架构 §4.4](../01design/01architecture.md) 的容量推算里，基础服务已占 14 GB / 64 GB，新增服务要从沙箱的 48 GB 里扣，**每 2 GB 就少一个沙箱**。

### 7.3 告警投递到哪

内网部署，没有确认过的邮件或 IM 通道。候选：写文件 + cron 巡检（最低要求）、企业微信 / 钉钉机器人（要出网或内网机器人地址）、Grafana Alerting（依赖 §7.1 选 A）。**没有通道的告警等于没有告警**，这一项定不下来的话，第 8 项要退回「只做体检脚本」。

### 7.4 `resumed` 的语义改还是不改

[P3 §8.7](./P3-plan.md) 移交：现在 `resumed = task.decisions is not None`，只标「审批之后的续跑」，崩溃恢复报 `false`。对前端的含义其实一样（别把已显示的对话重置）。

改的话要动事件契约（[ADR-0013](../01design/adr/0013-event-anticorruption-layer-v2-stream.md) 的防腐层）；不改的话要在契约文档里写清「`resumed=false` 不等于第一次开跑」，免得前端开工时踩。**前端未开工是改它的最好时机，也是最容易忘记它的时机。**

### 7.5 前端还要不要继续挂着

[P3 §7.3](./P3-plan.md) 定案「本期不做」，那是四期以来第一次它有明确处置。但 P4 做完之后，平台会是这样：**功能齐全、可观测、成本可控、没有任何人能用。**

成本看板尤其尴尬 —— 它是给人看的，而本期不做前端就只能返回 JSON。

**这一项不是 P4 的技术待决，是排期决策**，但必须在 P4 开工前问一次：P4 与前端，哪个先？若前端先，本期第 6 项（成本看板）应该跟着前端走，而不是做成一个没人看的端点。
