# ADR-0010：自建账号体系与三角色 RBAC

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-07-31 |
| 决策人 | hxy |
| 关联设计 | [安全设计 §7.2](../07security-design.md)、[数据设计 §6.2–§6.3](../06data-design.md) |

## 背景

平台面向学院教师及其课题组研究生（§2.2）。需要一并回答两个问题：账号从哪里来，权限怎么划分。

## 决策

1. **自建账号体系**，不对接学校统一身份认证
2. 三个角色：`admin` / `teacher` / `student`
3. 用户**可同属多个课题组**（`user_groups` 多对多关联表）
4. **不引入组内角色**（组长 / 成员）（2026-08-11 部分改写：不引入组内角色**表**，但引入 `groups.owner_id` 一列，见落地补记）
5. `teacher` 与 `student` 权限完全相同，**仅配额档位不同**

## 理由

**自建**：不依赖信息化部门的对接排期，也不受其接口可用性约束。本期定位是「先跑通」（§1.1），少一个外部依赖就少一个不可控因素。

**三角色**：`admin` 负责账号与配额管理，`teacher` / `student` 是使用者。管理员**不能查看他人的会话内容与上传数据** —— 这条边界写在数据访问层（§6.3），不做旁路。

**多组归属**：课题组之间存在交叉（一个学生可能参与多个课题），单外键无法表达。共享资源的可见性走**并集**。

**不引入组内角色**：权限判定会从「查 role」变成「查 role × 查该组内身份」，复杂度翻倍，而当前没有需要它的场景。

**师生同权**：课题组的语义是协作而非管理层级，让学生也能贡献 skill 与提示词符合实际使用方式。代价是共享资源没有质量把关 —— 应对方式是记录 `created_by` 使来源可追溯，而不是加审核流程。几人到十几人的课题组内，社交约束比技术约束有效。

## 被放弃的备选

| 备选 | 放弃理由 |
|---|---|
| **对接学校统一认证（CAS / OAuth）** | 依赖信息化部门的对接排期与接口可用性。省下的密码管理工作量不抵这份不确定性 |
| **单组归属**（`users.group_id` 单外键） | 无法表达跨课题参与。等有数据之后再改造，成本更高 |
| **组内角色（组长 / 成员）** | 权限判定复杂度翻倍，当前无场景 |
| **学生对共享资源只读** | 课题组是协作单元，限制学生贡献不符合实际使用方式 |

## 后果

**正面**：
- 不依赖外部系统，本期可独立推进
- 角色模型简单到只需一列 `role` + 一张关联表
- 表结构已为后续的 skill / 提示词共享预留（§1.2 的后续方向）

**代价**：
- 要自己管密码、找回与账号生命周期
- **没有学籍 / 教职工数据的自动同步**，账号需手工创建或批量导入
- **配额成为 `teacher` 与 `student` 唯一的区分手段**，因此 §6.4 的配额机制必须做 —— 否则这两个角色在系统里没有任何实际差别
- 组内共享资源无质量把关

## 落地补记（2026-08-08，P3）

**口令哈希用 argon2id（`argon2-cffi`），参数显式指定，不用库默认档。**

argon2id 是当前的推荐默认，内存硬度优于 bcrypt；bcrypt 另有 72 字节静默截断这个坑 —— 超长口令的后半截根本不参与计算，而这件事一声不响。

参数（`time_cost=3` / `memory_cost=64 MiB` / `parallelism=4`，即 RFC 9106 的第二组推荐值）写成模块顶常量而非依赖库默认，两个理由：将来调高时有据可查；**库改自己的默认值时，已部署系统的强度不会被静默改掉**。实现见 [`auth/password.py`](../../../app/auth/password.py)，另有一条用例断言哈希串里确实带着这三个参数。

**`groups` / `user_groups` 两张表本期不建**（[P3 计划 §7.6](../../03plan/P3-plan.md)）：没有任何组内共享资源挂在上面，而现在猜它们的字段与将来照实际需求建表成本相同，猜错却要迁移。上文「表结构已为后续的 skill / 提示词共享预留」这一条因此**尚未兑现** —— 角色模型（`users.role` 与 §7.2.1 那张权限表）照建不误，不建的只是「组」这个组织层级。

## 落地补记（2026-08-11）：组表建出，决策 4「不引入组内角色」部分改写

触发它的是本 ADR 自己列的重估条件之一 —— **「出现需要按组区分权限的实际需求」**：教师要凭邀请码招学生入组、增删名册、批入组申请。迁移 `0007_group` 建出三张表。

**上面推迟建表的判断得到兑现，不是被推翻。** 现在建出来的比 2026-07-31 猜的多了三样东西，而这三样恰恰是当时猜不出来的：`groups.owner_id`（组主）、`groups.invite_code`（注册准入凭证，全库唯一）、以及整张 `group_join_requests`（申请与审批）。当时若照猜的三列建出来，这次要迁移的正是它们。

**决策 4「不引入组内角色」改写成：不引入组内角色表，但引入一列组主。** 原理由是「权限判定会从『查 role』变成『查 role × 查该组内身份』，复杂度翻倍」—— 这条顾虑没有发生：判定仍然是一次等值比较（`group.owner_id == 当前用户`），没有矩阵，组员之间也仍然没有任何级别差异。

**决策 5「师生同权」不变**：组主可以是教师也可以是管理员，与全局 `role` 无关；`teacher` 与 `student` 的权限差别仍然只有配额档位。

**组仍然不改变任何数据可见性。** 组主看得到名册，看不到组员的会话、产物与用量 —— §6.3 那张隔离表一行未改。这是这次落地里最容易被顺手破掉的一条：把「教师能看学生用量」加进来只需要一个 join，而那条边界一旦开就收不回来。

**账号来源随之定型为三条**：`.env` 建的首个管理员（仅空库时）、管理员建的账号（教师唯一的来源）、自助注册（**一律是学生** —— 能自选角色等于能自选配额档）。自助注册填对邀请码即入组并可登录，不填则账号先停用，等管理员激活；两种「登不上」的状态在库里都是 `users.is_active = false`，不另立枚举，因为管理员对它们要做的是同一个动作。

## 重新评估的触发条件

- 用户范围扩大到全校，手工管账号不再可行
- 学院要求账号与校内统一身份保持一致
- ~~出现需要按组区分权限的实际需求~~ —— 已于 2026-08-11 触发，见上方补记
- 共享资源的质量问题实际发生
- 出现「组主之外还有人要管这个组」的需求（那时 `owner_id` 一列就不够了）
