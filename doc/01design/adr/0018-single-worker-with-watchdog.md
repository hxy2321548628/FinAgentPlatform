# ADR-0018：worker 降为单副本，进程存活由看门狗兜底

## 背景

P2 定下 `replicas: 2`，理由写得很清楚：**副本数解决的是「这个进程挂了怎么办」，不是吞吐** —— 吞吐来自 `WORKER_CONCURRENCY`，一个 asyncio 进程内并发驱动几十个 run（[ADR-0005](./0005-task-queue-redis-streams.md)）。当时还有第二个理由：验收标准③要实测 consumer group 的消费语义，两个副本才验得出「不重复也不丢」。

复核这条决策时发现，「一个进程内并发几十个 run」在实现上并不成立：DeepAgents 的十个 `a*` 方法默认实现是 `asyncio.to_thread(自己的同步版本)`，而本平台的沙箱 backend 只实现了同步那一半，于是**每一次工具调用都占一个线程池名额**。默认线程池上限是 `min(32, cpu+4)`，在部署机上算出来正好是 20，与 `WORKER_CONCURRENCY` 相等 —— 零余量，且这个数随机器核数变动、没人配过、超了也不报错。

也就是说，两个副本当时确实在买并发能力，只不过买的是线程池名额，而不是任何人写下来的理由。

## 决策

三条一起，缺一条这个决策就是坏的：

1. **worker 降为单副本**，去掉 `deploy.replicas`。
2. **沙箱 backend 改成全异步**：覆写协议的十个 `a*` 方法，删掉同步那十个（基类默认抛 `NotImplementedError`）。线程池那道隐式闸就此消失，`WORKER_CONCURRENCY` 成为进程内唯一的并发上限。
3. **worker 内置看门狗**：守护线程盯着事件循环定期盖的时间戳，超时未更新即结束进程（`os._exit`），交给 Docker 的 `restart: unless-stopped` 拉回来。

## 理由

**第一，副本数买到的那部分并发，可以用更明确的方式买回来。** 拆掉 `to_thread` 之后并发只由一个显式旋钮决定，而不是「两个进程各自一个随核数变动的线程池」。同一件事，从两处隐式变成一处显式。

**第二，单进程覆盖得了「崩溃」，覆盖不了「卡死」，而后者原本也没被覆盖。** 进程退出（OOM、未捕获异常）由 `restart` 拉回；消息留在 pending 里，重启后由 `XAUTOCLAIM` 认领回来 —— 那条命令只看消息闲置了多久、不看它归谁，因此单副本下认领的就是重启后的自己，这条路与双副本时一样通。**真正的缺口是「进程还活着但事件循环不转了」**：Docker 的 `restart` 只认进程退出，健康检查判出 unhealthy 并不会重启容器（那是 Swarm 才有的行为）。双副本时这个缺口由兄弟进程遮住了一半（新任务还有人领），但那个卡住的进程手上的 run 一样要等到认领阈值才被救走。看门狗把这个缺口正面堵上，且对双副本同样有价值。

**第三，双副本有一个单副本没有的失效模式。** 认领判据是「消息闲置多久」，健康的 worker 靠每 15 秒一次 `touch` 把它归零。事件循环若有一次超过 60 秒的停顿，兄弟副本就会把它手上的消息抢走 —— 同一个 run 并发跑两遍、共用一个沙箱、写同一份 checkpoint。单进程有 `_held` 挡着，自己不会抢自己。

**第四，单机部署下的冗余本来就是半截的。** [ADR-0001](./0001-single-host-compose.md) 是单机 Compose，两个进程同生共死于一台机器；主机故障这个主导失效模式，两个副本一个也挡不住。

## 被放弃的备选

| 备选 | 放弃理由 |
|---|---|
| **维持 `replicas: 2`** | 它买到的并发在第 2 条落地后不再需要；而它带来的「健康 worker 被抢消息」是真实代价 |
| **加 compose `healthcheck`** | **达不到目的**：`restart` 只认进程退出，判出 unhealthy 不会重启容器。只有可观测性价值，没有恢复价值 |
| **autoheal 边车容器** | 能把 unhealthy 变成重启，但要再给一个容器挂 `docker.sock`，为一件进程自己就能做的事扩大了 [ADR-0004](./0004-sandbox-broker-docker-sock.md) 的暴露面 |
| **看门狗做成 asyncio 任务** | 事件循环卡住时，跑在它上面的救兵一起卡住。必须是线程 |
| **在容器内 `kill -9 1` 制造真崩溃**（验收用） | 内核不向 PID 1 投递来自本命名空间的 SIGKILL，做不到 |

## 后果

**正面**：
- 并发上限只剩一处、且是显式配置的；
- 「进程卡死」这一类第一次被覆盖，而它此前在双副本下也只被遮住一半；
- 少一个进程的连接池（每副本 5 个 Postgres 连接 + 10 个 checkpoint 连接）与一半的日志噪音；
- 消灭了「健康 worker 的消息被兄弟副本抢走」这条双重执行路径。

**代价**：
- **一次崩溃的爆炸半径翻倍**：一个进程带着 `WORKER_CONCURRENCY` 条 in-flight run，崩一次全部从 checkpoint 重跑，重烧的 token 是真金白银；
- **`make rebuild` 会静默一段**：`stop_grace_period` 是 30 分钟，排空期间没有别的进程在领任务。任务留在 Stream 里不会丢，只是要等；
- **看门狗误判的代价不小**：60 秒完全无响应才动手，但真误判一次就是上面那个爆炸半径。阈值定在 `worker/watchdog.py` 的模块常量里，不是 Settings；
- **外部 `docker kill` 不会被拉回**：Docker 把外部的 kill / stop 记成「人工停止」，`restart` 对这一类故意不生效。这不影响生产（真崩溃是进程自己退出），但**验收脚本必须自己把容器拉回来**，否则它验的是一个产品里不存在的场景。

## 重新评估的触发条件

- 单机撑不住，需要跨主机部署 → 副本数与调度一起重谈（[ADR-0001](./0001-single-host-compose.md) 的触发条件先成立）；
- 一次崩溃损失的 token 变得不可接受 → 把 `WORKER_CONCURRENCY` 调小并加副本，用更小的爆炸半径换回冗余；
- 看门狗出现误杀 → 先调阈值，反复误杀则说明事件循环里有该拆走的阻塞调用，那是要修的 bug 而不是要调的参数；
- broker 成为并发瓶颈（它的 `execute` 仍在 `asyncio.to_thread` 上，同一个 `min(32, cpu+4)`）→ 那一侧的线程池要显式配置，与本条决策无关但常被一起问起。
