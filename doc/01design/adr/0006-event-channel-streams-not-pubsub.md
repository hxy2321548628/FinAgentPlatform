# ADR-0006：事件通道用 Redis Streams，不用 Pub/Sub

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-07-29 |
| 决策人 | hxy |
| 主文档关联 | §4.2 三条独立通道、§5.2 事件流与断线重放 |

## 背景

worker 执行过程中会持续产生事件（token 增量、工具调用、中间步骤、审批请求），需要推送给前端。worker 不直连前端，事件要经过网关中转（§4.1）。

需要决定 worker 与网关之间用什么传递事件。Redis Pub/Sub 是最直觉的选择。

## 决策

**每个 run 一条独立的 Redis Stream**，worker `XADD` 写入，网关 `XREAD` 读出后转成 SSE 推给前端。

```
worker ──XADD──▶ stream:run:{run_id} ──XREAD──▶ 网关 ──SSE──▶ 前端
                        │
                        │ 异步归档
                        ▼
                  Postgres run_events
```

Stream 设 `MAXLEN` 或 TTL 控制内存占用，同时异步归档到 Postgres 做长期存储。

## 理由

**Pub/Sub 不持久化。** 消息发出的瞬间，没有订阅者接收就永久消失。

对本平台这是致命的：一次分析可能跑几十分钟，期间教师刷新页面、切换网络、笔记本合盖休眠都是常态。用 Pub/Sub 的话，**中间过程会永久丢失** —— 教师重连后只能看到一片空白，然后等待剩余部分，前面 20 分钟的推理过程和中间结果全部无从找回。

Stream 是持久的消息日志，配合 SSE 天然携带的 `Last-Event-ID` 请求头，断线重连时从上次的 event id 继续读，**中间产生的事件全部补齐**。这让「刷新页面」从一个破坏性操作变成一个无害操作。

顺带的收益：Stream 的事件日志可以直接异步归档到 Postgres，成为 run 的执行历史，无需另建一套记录机制。

## 被放弃的备选

| 备选 | 放弃理由 |
|---|---|
| **Redis Pub/Sub** | 不持久。断线即永久丢失中间过程。**这是本决策要解决的核心问题** |
| **worker 直连前端推流** | 绕过网关意味着鉴权无法集中、worker 需要暴露到前端可达的网络位置，安全性与架构清晰度都变差 |
| **只写 Postgres，网关轮询** | 持久性没问题，但轮询延迟与数据库压力都不适合 token 级别的高频增量推送 |
| **Kafka** | 持久性与回溯能力更强，但为几十并发的场景引入 Kafka 是明显的过度设计 |

## 后果

**正面**：
- 断线重连可完整补齐，教师侧体验从「不敢刷新」变成「随便刷新」
- 事件日志天然可归档，run 历史无需另建机制
- 与任务队列复用同一个 Redis（[ADR-0005](./0005-task-queue-redis-streams.md)），不引入新组件

**代价**：
- **Stream 占用 Redis 内存**，必须配 `MAXLEN` 或 TTL，否则长跑任务会把内存吃满。这个上限值需要按实际事件量调整
- `MAXLEN` 截断与归档之间存在竞争：若归档慢于截断，会丢失未归档的事件。归档链路需要保证跟得上
- 每个 run 一条 Stream 意味着 key 数量随 run 数增长，需要可靠的清理机制，否则会积累大量僵尸 key
- 网关侧需要为每个 SSE 连接维持一个 `XREAD` 循环，连接数上升时需关注网关的资源占用

## 重新评估的触发条件

- Redis 内存因 Stream 频繁告警，且调 `MAXLEN` 无法解决
- 需要长期（数月）保留完整事件流并支持回溯查询 → 考虑专门的日志存储
